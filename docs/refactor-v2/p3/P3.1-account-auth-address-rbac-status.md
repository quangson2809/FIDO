## Implemented on the candidate

- Canonicalizes supported Vietnamese phone input to `+84` plus nine digits before registration/login/staff/bootstrap lookup and writes; ambiguous legacy aliases fail closed.
- Registration creates an ACTIVE Account and assigns the seeded `CUSTOMER` Role in one transaction. New staff Accounts start ACTIVE; passwords are hashed and never returned.
- Active-phone uniqueness applies to non-soft-deleted Accounts; soft deletion releases the phone for reuse.
- Login returns a generic unauthorized response for unknown/ambiguous phone and wrong password. A valid password for non-ACTIVE Accounts does not receive a token; protected JWT requests re-check current Account status and effective active Roles/Permissions.
- `/me` and address operations derive scope from the JWT subject. Address lookups are owner-scoped; address mutations serialize on the owning Account row.
- Migration V9 renames `accounts.account_id` to target `accounts.id`; JPA Account mapping uses `id`. V10 renames `addresses.address_id` to `addresses.id` and adds structured address columns.
- Staff and RBAC mutations use Controller → Service → Repository, validate role grants, protect system roles/seed permissions, and serialize last-SUPERADMIN changes on the locked `SUPERADMIN` Role row.
- Permission creation and its `SUPERADMIN` grant share one transaction. SUPERADMIN remains ACTIVE with the complete Permission catalogue; Role/Permission codes are immutable.
- Staff/RBAC mutation paths call P3.0 `AuditWriteService` within the caller transaction. V11 adds target audit fields while retaining legacy columns/history. The earlier statement that the writer was not enabled is stale and is corrected here.
- The sole saved Address remains default if a PATCH requests `is_default=false`; a regression test was added in commit `6644dafd90b4c4f468289fb275a54b20fdbdf741`. CI for that exact commit must be checked before treating this fix as verified.

## Remaining hard blockers

1. **Legacy saved-address rows are not fully mappable to the target contract.** V10 deliberately leaves structured recipient/location columns nullable because existing `address_text` cannot be safely decomposed into recipient name/phone/province/district/ward/address line. New addresses require complete fields and an incomplete legacy row can be repaired only when all structured fields are supplied, but `GET /me` can still expose null structured fields for untouched legacy rows. Do not fabricate recipient/location data. Resolve via the approved clean-reset/data-disposition policy or an owner-approved legacy-address handling rule before claiming full target Address acceptance.
2. **Account target nullability remains a compatibility gap.** `accounts.full_name` remains nullable to preserve old rows lacking a trustworthy name backfill, although new registration/staff creation require a nonblank name. The target schema and API contract require a value. Do not invent names for legacy accounts; align clean-reset/data disposition before tightening the column.
3. **End-to-end clean-reset target verification remains required.** V9–V11 bridge the current runtime schema and the prior backend workflow passed, but a clean target DDL/Data Dictionary comparison and full consumer mapping audit must confirm the whole 31-table target, all FK references and legacy audit-read compatibility before P3.1 is accepted. Do not add new tables/columns beyond the approved target.
4. **Required audit coverage is limited to the implemented call sites.** Staff/RBAC mutations are wired to P3.0; do not infer that every Account or other domain mutation has audit coverage without call-site verification.
