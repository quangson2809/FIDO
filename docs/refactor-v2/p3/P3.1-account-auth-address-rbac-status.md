## Design decisions

Keep the established Controller → Service → Repository path, explicit request/response DTOs and manual mapping. Use the approved phone canonicalizer, Spring Security principal resolution, transaction boundaries for Account + CUSTOMER and Permission + SUPERADMIN grant, and the existing locked SUPERADMIN role row as the serialization point for lifecycle/grant changes. No permission DSL, generic CRUD superclass, per-role Factory, Chain of Responsibility, event bus or outbox was introduced.

## Implemented on this candidate

- Canonicalize supported national/international Vietnamese phone forms to \`+84\` plus nine digits before registration/login/staff/bootstrap lookup and writes. Lookup checks canonical and legacy national representations; ambiguous legacy matches fail closed.
- Migration V7 seeds \`CUSTOMER\` idempotently and grants all current Permission rows to \`SUPERADMIN\`. Registration requires \`full_name\`, then creates an ACTIVE account, assigns CUSTOMER and prepares a token in one transaction.
- Migration V8 introduces transitional Account \`status\`, \`deleted_at\`, generated \`phone_active_key\`, Role \`status\`, and Permission \`description\`. The old unconditional phone unique index is replaced by a unique index over the non-soft-deleted phone key, so a soft-deleted account no longer reserves its phone.
- Correct phone uniqueness checks consider only non-soft-deleted rows. Login performs a dummy password-hash check for missing/ambiguous identities; unknown phone and wrong password return the same 401 shape. A valid password for a non-ACTIVE account returns 403 without a token.
- Protected JWT requests re-read the account and current active Roles/Permission grants from the database; non-ACTIVE or soft-deleted accounts fail principal resolution. INACTIVE Roles do not contribute effective grants and cannot be newly assigned.
- \`PATCH /api/v1/me\` accepts only \`full_name\` and \`email\`; phone is not patchable because no phone-change/verification workflow is approved. Saved Address ownership is always queried using both address ID and principal account ID, with an account row lock serializing its current mutations.
- Staff Account mutation supports the approved profile/status fields and role replacement. The SUPERADMIN role-row lock serializes last-active-SUPERADMIN checks; the rule counts assigned accounts that are ACTIVE and not soft-deleted.
- System roles CUSTOMER/ADMIN/SUPERADMIN cannot be deleted. Permission codes remain immutable; seeded Permission codes are protected; custom Permission deletion is rejected while any non-SUPERADMIN Role uses it. Creating a Permission and granting it to SUPERADMIN occurs in one transaction. SUPERADMIN cannot be deactivated or have its full Permission set reduced.
- Added H2 tests for canonicalization, duplicate alias rejection, soft-delete phone reuse, non-ACTIVE login/protected requests, inactive Role authorization, Permission/SUPERADMIN grant atomicity, system safeguards, and concurrent removal of the last active SUPERADMIN assignment.

## Hard blockers for full P3.1 acceptance

These are source/schema integration blockers, not naming or pattern decisions.

1. **Account physical mapping is still legacy.** Runtime Flyway keeps primary key \`accounts.account_id\`, whereas target clean-reset DDL uses \`accounts.id\`. V8 deliberately adds lifecycle columns without renaming the PK, because the legacy key is referenced by Cart, Order, Payment, Goods Receipt, Inventory Transaction, Audit Log and Content Page foreign keys. These FK mappings, raw SQL, dev seed probes and migration constraints must be coordinated before the target PK rename. The runtime \`full_name\` column remains nullable to preserve legacy rows for which no owner-approved name backfill exists; new registration/staff creates require it.
2. **Target Address schema is not available at runtime.** Existing rows contain only \`address_text\`; target requires recipient identity, recipient phone, province/district/ward, address line and default-address invariants. A migration cannot safely infer those fields from free text. Current APIs therefore preserve the legacy Address DTO and do not meet P1.2's structured Address/default-promotion contract. Ownership isolation remains in place.
3. **P3.0 target audit writer is not enabled.** Runtime \`audit_logs\` still uses legacy \`audit_id/target_type/target_id/description\` columns. P3.0's \`AuditWriteService\` writes the approved target \`id/entity_type/entity_id/before_data/after_data/correlation_id\` contract and must not be called against the legacy table. Existing account/RBAC mutation callsites still use the legacy \`AuditService\`; target-schema audit integration and its atomicity acceptance remain open until audit schema/read-model alignment is delivered.
4. **Full target-schema alignment is not complete.** Physical IDs and Address columns still diverge from owner-approved ERD/Data Dictionary. Role/Permission lifecycle semantics are now represented, but a target-schema reset/mapping verification is still required once the cross-module FK plan and non-fabricating legacy-data policy are approved.
5. **MySQL concurrency acceptance is pending.** The race test is part of the H2 suite. Current CI MySQL stage verifies migration/mapping but does not run the new last-ACTIVE-SUPERADMIN race against MySQL. Run it against MySQL after the Account/FK migration strategy is finalized.
