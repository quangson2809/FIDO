**Candidate branch:** \`feature/p3-1-account-rbac\`  
**Base:** \`demo1\` at \`d60e4ade7560f0da358965197a2a8b33a044b9c1\`  
**Status:** PARTIAL — do not merge as P3.1 accepted until the hard blockers below are resolved.

## Design decisions

Keep the established Controller → Service → Repository path, explicit request/response DTOs and manual mapping. Use a small phone canonicalizer for the already-approved Vietnam phone identity rule, the existing Spring Security principal/method authorization, a transaction around account-plus-role writes, and the existing locked SUPERADMIN role row as the serialization point for RBAC/last-SUPERADMIN mutations. No permission DSL, generic CRUD superclass, per-role Factory, Chain of Responsibility, event bus or outbox was introduced.

## Implemented on this candidate

- Canonicalize supported national and international phone forms to \`+84\` plus nine digits before registration/login/staff/bootstrap lookup and writes. During transition, lookups check both the canonical and legacy national representation; an ambiguous legacy match fails closed.
- Add an idempotent Flyway migration to seed the required \`CUSTOMER\` role. Registration saves the account, grants \`CUSTOMER\`, and issues the access token in one transaction.
- Keep unknown phone/password login responses identical at the HTTP status level and retain the dummy password-hash comparison for missing or ambiguous identities.
- Remove phone from \`PATCH /api/v1/me\`; no approved phone-change/verification workflow exists.
- Protect all three system role codes from deletion; reject duplicate permission IDs; prevent patches from reducing the SUPERADMIN permission set; disallow permission-code updates; automatically grant each newly created permission to SUPERADMIN in the same transaction.
- Protect P1.8 seeded permission codes from deletion. A custom permission may be deleted only if no non-SUPERADMIN role references it; its SUPERADMIN relation and row are removed in the same transaction.
- Expand tests for phone canonicalization/alias collisions, customer role assignment, permission grants, immutable permission code, and rollback of both permission and SUPERADMIN grant when the existing audit insert fails.

## Hard blockers for full P3.1 acceptance

These are source/schema integration blockers, not naming or pattern decisions.

1. **Runtime Account schema is still legacy.** Flyway runtime migrations V1–V6 use \`accounts.account_id\`, with no \`full_name\`, \`status\` or \`deleted_at\`; active-phone uniqueness is therefore not representable as approved. The target clean-reset schema uses \`accounts.id\`, required account fields, status, soft-delete and a generated active-phone key. The legacy account primary key is referenced by Cart, Order, Payment, Goods Receipt, Inventory Transaction, Audit Log and Content Page foreign keys; changing it safely must coordinate all those mappings.
2. **Target Address schema is not available at runtime.** Existing rows only have \`address_text\`; target requires recipient identity, province/district/ward, address line and default-address invariants. A migration cannot safely infer those facts from the free-text legacy field. Current address APIs remain legacy and do not meet P1.2's structured DTO/default-address contract, although ownership queries continue to scope lookup by both address and principal account.
3. **Account lifecycle and protected-request enforcement are incomplete.** The runtime entity has no status/deleted marker and Role has no active/inactive status. Consequently the current runtime cannot reliably reject non-ACTIVE accounts/tokens, implement soft-delete phone reuse, or filter grants contributed by INACTIVE roles. No fake hard-coded lifecycle/status has been introduced.
4. **P3.0 target audit writer is not enabled.** Runtime \`audit_logs\` still uses the legacy \`audit_id/target_type/target_id/description\` columns. P3.0's \`AuditWriteService\` writes the approved target \`id/entity_type/entity_id/before_data/after_data/correlation_id\` contract and must not be called against the legacy table. Existing account/RBAC mutations still use the legacy AuditService, so target-schema P3.0 audit integration and its atomicity acceptance remain open until the schema/read-model alignment phase is completed.
5. **DTO/schema mismatch remains.** The runtime Account DTO and registration/staff/address APIs do not yet include all P1.2 fields (\`full_name\`, structured Address fields, descriptions/statuses) because their owning target columns are not present. These APIs must be migrated together with the approved schema and consumers; this candidate does not silently fabricate missing data.
