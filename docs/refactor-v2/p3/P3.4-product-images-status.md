# P3.4 — Product Images, Gallery Ordering and Order Snapshot Reference

**Branch:** `feature/p3-1-account-rbac`  
**Scope:** Product gallery persistence/mutations and the existing Order image snapshot. No schema change, frontend work, provider replacement, remote deletion, or retention job.

## Implemented

- Gallery commands serialize on the owning Product row and lock the ordered image rows before validation/mutation.
- Every accepted non-empty gallery has one primary image at `sort_order = 0`; every other image is non-primary. An empty gallery has no primary.
- Append, remove, reorder and Product's existing full-gallery replacement write primary state together with sort order inside the database transaction.
- Reorder/remove normalization temporarily vacates the unique positions before writing the dense final order, avoiding transient collisions on `uq_product_images_product_order`.
- Existing invalid gallery data (gaps, incorrect ordering or a primary mismatch) fails closed with HTTP 409. The command does not silently repair populated legacy data; any existing-data repair requires the separately approved preflight/migration described by the owner amendment.
- Gallery detail responses use deterministic `sort_order ASC, id ASC` order and expose the P1.3 image DTO fields `id`, `image_url`, `is_primary`, and `sort_order`.
- Order placement continues to copy the selected current primary image URL into `order_items.image_url_snapshot`. Gallery reorder/removal does not update that Order snapshot. Remote asset deletion remains unavailable to gallery code.

## Storage/version and retention limitation

The approved 31-table schema stores `product_images.image_url` and `order_items.image_url_snapshot` as `VARCHAR(1000)`; it has no separate object-version column or asset registry. The current `ImageStorageGateway.UploadedImage` contract contains only the returned URL, and `ImgBbImageStorageClient` returns the provider's direct URL. This phase preserves that narrow upload-only adapter and the exact URL captured at Order placement.

The application has no operation that overwrites or deletes a previously uploaded provider asset. However, source inspection alone cannot prove that ImgBB/provider-side content will remain resolvable and byte-identical for the entire future Order-history window, or that the direct URL is a formal immutable version identifier. That guarantee remains **unverified**. Guaranteeing it requires an explicit provider-level immutability/lifecycle commitment or a separately approved storage/schema design; this phase does not invent an asset registry, provider framework, new DDL, or additional version column.

The numeric image retention period and any lawful deletion/anonymization exceptions remain TBD under DB-12. No purge job, garbage collector, remote delete path, or provider lifecycle rule was introduced.
