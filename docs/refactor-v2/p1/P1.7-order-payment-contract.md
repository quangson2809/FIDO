# P1.7 — Order, Snapshot, COD, Shipping and Refund Contract

**Disposition: CONTRACT SPECIFIED; runtime acceptance is pending P3.10.** This phase changes normative documentation only. It does not implement an Order lifecycle, run a migration, change the approved ERD, or integrate a payment gateway or carrier.

## 1. Authority, boundaries and reconciliation

- The approved 31-table ERD v2 and the physical field contract in [P1-data-dictionary.csv](P1-data-dictionary.csv) remain authoritative. This document defines how existing Order, Payment, ShippingInfo, Inventory, Voucher and Audit rows cooperate; it does not authorize a new table or column.
- P1.4 owns Inventory balance/ledger mechanics, source-derived deduplication and locking. P1.5 owns money formulas and Voucher quota semantics. P1.6 owns Cart, order-create request fingerprint/idempotency/replay. **P1.7 owns post-create Order transitions, COD collection/refund timing, manual shipping and cancellation's one-time Voucher release.** P3.10 implements and tests these transitions.
- The target remains authenticated checkout, single merchant, COD only, one operational warehouse and manual shipping. No online payment gateway, carrier API, event callback, separate Order timeline, payment-event, refund-event or return-line table is implied.
- Order placement creates a `PENDING` Order. Inventory is checked at placement but **not reserved or deducted until `PENDING → CONFIRMED`**. The confirmation command rechecks and deducts stock atomically. This follows the approved Order graph in [06-business-rules-state-machines.md](../../06-business-rules-state-machines.md) and resolves the older shorthand “place order updates stock”: the placement transaction does not post an `ORDER` inventory movement.
- Existing route conventions and permissions are retained. This contract uses the documented `ORDER_READ`, `ORDER_EDIT`, `ORDER_PAYMENT` and `ORDER_AFTER_SALES` capabilities; P1.8 owns role/permission seed assignment. Do not invent extra persisted role or permission models in P1.7.

## 2. Aggregate states

### 2.1 Order state graph

```text
PENDING -> CONFIRMED -> PREPARING -> SHIPPING -> COMPLETED -> RETURNED
   |           |            |           |
   v           v            v           v
CANCELLED   CANCELLED    CANCELLED   DELIVERY_FAILED -> SHIPPING (manual retry)
                                         |
                                         v
                                      CANCELLED
```

Allowed Order transitions are exactly the rows below. A state not listed as a destination is terminal for the public target contract.

| From → to | Actor / permission | Preconditions | Atomic effects |
|---|---|---|---|
| create → `PENDING` | Authenticated customer placing the Order; P1.6 | Non-empty current Cart; valid request, recipient, current quote inputs and optional Voucher; account-scoped create key is new, or replay rules apply | P1.6 creates Order and immutable snapshots, COD Payment `UNPAID`, ShippingInfo `PENDING`, consumes Cart and increments applicable Voucher usage; no inventory movement. |
| `PENDING → CONFIRMED` | Authorized operator, `ORDER_EDIT` | Order is still `PENDING`; lock its OrderItems and the one operational warehouse's balances; each ordered quantity is currently available | Insert one negative `ORDER` movement per OrderItem, update balance/version and audit; set Order `CONFIRMED`. Any shortage, duplicate source or audit failure rolls back the whole transition. Prices and snapshots are not recalculated. |
| `CONFIRMED → PREPARING` | Authorized operator, `ORDER_EDIT` | Order is `CONFIRMED`; the confirmation stock movements exist exactly once | Set Order `PREPARING`; write audit. No further stock movement. |
| `PREPARING → SHIPPING` | Authorized operator, `ORDER_EDIT` | Order is `PREPARING`; shipping can be handed to the manual delivery process | Set Order `SHIPPING`, ShippingInfo `SHIPPED`, record/update available dispatch timestamp and operator-provided carrier/tracking data if present in schema; audit. No carrier integration is called. |
| `SHIPPING → DELIVERY_FAILED` | Authorized operator, `ORDER_EDIT` | Order is `SHIPPING`; delivery has been manually reported as failed; COD has not been collected | Set Order `DELIVERY_FAILED`, ShippingInfo `FAILED`; record the transition in AuditLog. Do not restore inventory, refund, release Voucher quota or complete Payment. A failure reason may be supplied for the audit payload; no new reason column is inferred. |
| `DELIVERY_FAILED → SHIPPING` | Authorized operator, `ORDER_EDIT` | Order is `DELIVERY_FAILED`; Payment remains `UNPAID`; a manual retry is authorized | Set Order `SHIPPING`, ShippingInfo `SHIPPED`, update available last-dispatch timestamp/details and audit. Do not deduct stock a second time. |
| `PENDING → CANCELLED` | Authorized operator, `ORDER_EDIT` | Order is `PENDING`; Payment is `UNPAID`; dispatch has not begun | Set Order `CANCELLED`, ShippingInfo `CANCELLED`; release one previously consumed Voucher use if this Order used one; audit. No inventory reversal because no `ORDER` movement exists. |
| `CONFIRMED → CANCELLED` | Authorized operator, `ORDER_EDIT` | Order is `CONFIRMED`; Payment is `UNPAID`; dispatch has not begun | Set Order/ShippingInfo to `CANCELLED`; post an exact linked positive cancellation reversal for every original `ORDER` deduction; release the Order's Voucher use once if applicable; audit. |
| `PREPARING → CANCELLED` | Authorized operator, `ORDER_EDIT` | Order is `PREPARING`; Payment is `UNPAID`; dispatch has not begun | Same atomic compensation as `CONFIRMED → CANCELLED`: one exact stock reversal per original deduction, one eligible Voucher release, cancel ShippingInfo, set Order `CANCELLED`, audit. |
| `DELIVERY_FAILED → CANCELLED` | Authorized operator, `ORDER_EDIT` | Order is `DELIVERY_FAILED`; Payment remains `UNPAID`; a retry will not be attempted | Set Order/ShippingInfo to `CANCELLED`; reverse previously deducted stock exactly once; release the Voucher use once if applicable; audit. |
| `SHIPPING → COMPLETED` | Authorized operator, `ORDER_PAYMENT` | Physical delivery and COD collection have both been verified manually; Order is `SHIPPING`, ShippingInfo `SHIPPED`, Payment `UNPAID`; collection amount equals Payment/Order total | In one command, set Order `COMPLETED`, ShippingInfo `DELIVERED`, Payment `PAID`; capture authenticated collector and server timestamp; audit. If any write fails, none commits. This is a manual attestation, not a gateway transaction. |
| `COMPLETED → RETURNED` | Authorized operator, both `ORDER_AFTER_SALES` and `ORDER_PAYMENT` | Order `COMPLETED`; Payment `PAID`; the operator confirms the whole-order return and an offline full COD refund; required reason supplied; Payment has not been refunded | In one transaction, set Order `RETURNED`, Payment `REFUNDED`, set refund amount equal to the full Payment amount and write refunded actor/time/reason plus audit. Never accept a client-chosen refund amount. No automatic stock restock and no Voucher quota release. |

No other Order transition is authorized in v1. In particular, cancellation from `SHIPPING` or `COMPLETED` is rejected; a shipping attempt must first be marked `DELIVERY_FAILED` before cancellation can be considered. A completed Order can become `RETURNED` only through the combined full-return/full-refund command. Customer-side order cancellation and recipient-snapshot editing are not public v1 commands in the target API; do not infer them from legacy routes.

### 2.2 Payment state/operation matrix

| Payment state | Allowed operation | Required actor/precondition | Result |
|---|---|---|---|
| `UNPAID` | Collect COD | `ORDER_PAYMENT`, with physical delivery confirmed while Order is `SHIPPING` and ShippingInfo is `SHIPPED` | Only the atomic `SHIPPING → COMPLETED` command can collect. Set `PAID`, collector actor and server time; amount is the persisted full Order total. |
| `UNPAID` | Refund | None | Reject: a cancelled/uncollected COD order has no collected payment to refund. |
| `PAID` | Refund full amount | `ORDER_AFTER_SALES` + `ORDER_PAYMENT`, Order `COMPLETED`, verified whole-order return and offline refund | Combined `COMPLETED → RETURNED`; set `REFUNDED`, `refund_amount = amount`, actor/time/reason. |
| `PAID` | Collect again | None | `409 PAYMENT_ALREADY_COLLECTED`; no write or second audit side effect. |
| `REFUNDED` | Collect or refund again | None | `409 PAYMENT_ALREADY_REFUNDED`; no write or second payout. |

There is exactly one COD Payment aggregate per Order. v1 supports at most one **full** refund of the paid amount. Partial refunds, multiple refund operations, gateway transactions/IDs/callbacks, automated cash disbursement and a refund ledger are out of scope. The successful refund command records that a staff actor completed the offline COD refund; it does not transfer money itself.

### 2.3 ShippingInfo state matrix

| From → to | Trigger | Preconditions/effects |
|---|---|---|
| create → `PENDING` | Order placement | One ShippingInfo row per Order; initialize from the Order's immutable recipient snapshot. |
| `PENDING → SHIPPED` | `PREPARING → SHIPPING` | Authorized manual dispatch; set available dispatch data/timestamp and audit. |
| `SHIPPED → FAILED` | `SHIPPING → DELIVERY_FAILED` | Manual failure report; require Payment `UNPAID`; audit failure reason if supplied. |
| `FAILED → SHIPPED` | `DELIVERY_FAILED → SHIPPING` | Authorized manual retry; no extra inventory deduction. Current fields represent latest state, not a list of attempts. |
| `SHIPPED → DELIVERED` | `SHIPPING → COMPLETED` | Only together with one-time COD collection. |
| `PENDING → CANCELLED` or `FAILED → CANCELLED` | Allowed Order cancellation | Update in the same cancellation transaction. |

All other ShippingInfo transitions are rejected. Manual shipping fields are allowed only when those fields already exist in the target schema; carrier/tracking values are descriptive, not proof of a carrier API integration. Order/Payment/Shipping states are updated as one logical command and must never contradict one another on commit.

## 3. Order-use cases and actor rights

| Use case | Actor and access | Contract / rejection rules | Target persistence |
|---|---|---|---|
| Place Order | Authenticated customer | P1.6: account-scoped idempotency; reprice; create snapshots/Payment/ShippingInfo; consume Cart and eligible Voucher use; no stock reservation/deduction. | `ORDERS`, `ORDER_ITEMS`, `ORDER_ADDRESSES`, `ORDER_VOUCHER_SNAPSHOTS`, `PAYMENTS`, `SHIPPING_INFOS`, `CARTS`, `CART_ITEMS`, `VOUCHERS`, `AUDIT_LOGS` |
| Read own order/history | Authenticated customer | Scope by principal; never return another Account's Order. Current Order status can change but order-line/address/voucher snapshots are stable. | Order tables + `PAYMENTS` + `SHIPPING_INFOS` |
| Read/search administrative Orders | Staff with `ORDER_READ` | All filters/pagination server-side; no mutable catalog fields substituted for snapshots. | Order tables + Payment/ShippingInfo |
| Confirm stock | Staff with `ORDER_EDIT` | Recheck under lock; shortage or duplicate semantic movement aborts entire command. | `ORDERS`, `ORDER_ITEMS`, `INVENTORIES`, `INVENTORY_TRANSACTIONS`, `AUDIT_LOGS` |
| Prepare, dispatch, fail, retry or cancel | Staff with `ORDER_EDIT` | Transition table above is authoritative; cancellation includes exact stock reversal when deduction exists and one-time Voucher release where eligible. | `ORDERS`, `SHIPPING_INFOS`, optionally inventory tables and `VOUCHERS`, `AUDIT_LOGS` |
| Complete delivery/collect COD | Staff with `ORDER_PAYMENT` | Physical delivery and collection must be confirmed together; no client-supplied actor, timestamp or alternate amount. | `ORDERS`, `PAYMENTS`, `SHIPPING_INFOS`, `AUDIT_LOGS` |
| Accept whole-order return and full refund | Staff with `ORDER_AFTER_SALES` and `ORDER_PAYMENT` | One-time terminal `COMPLETED → RETURNED`; full amount only; requires reason; no per-line quantities or partial refund. | `ORDERS`, `PAYMENTS`, `AUDIT_LOGS` |

Customer self-cancellation is not exposed by the target routes in this phase. A new customer cancellation endpoint, separate return receipt/inspection workflow, refund retry ledger, or detailed item-level return/exchange behavior requires explicit approval and a corresponding API/schema design.

## 4. Snapshot policy — historical Order facts

Snapshots are captured at successful Order placement (P1.6 transaction), and are thereafter immutable. The detail/read path must be satisfied from the Order plus snapshot/payment/shipping rows; it must not use the current Product or Voucher record to reconstruct history.

| Source at placement | Stored target fields / table | Rule |
|---|---|---|
| Product identity | `ORDER_ITEMS.product_id` | Preserve identity/reference only. The referenced Product can be inactive later; the Order still uses its stored facts. Do not change this to `variant_id`. |
| Product SKU/name | `ORDER_ITEMS.sku_snapshot`, `product_name_snapshot` | Copy the exact normalized display and SKU values at placement. Product edits/rename/deactivation never rewrite them. |
| Product attributes | `ORDER_ITEMS.attribute_snapshot` | Store the order-time attribute facts as a JSON snapshot. Deterministic ordering is by stable Attribute identity/code; preserve both the displayed label/value needed to explain what was ordered. Do not rebuild the JSON from live Product attributes/Options. |
| Product image | `ORDER_ITEMS.image_url_snapshot` | Store a stable immutable object/version reference, not a mutable gallery slot or “current primary image” query. Preserve access during the required retention window; the numeric retention period remains TBD. Product image reorder/remove/change must not rewrite the snapshot. |
| Quantity and money | `ORDER_ITEMS.quantity`, `unit_price`, `discount_amount`, `line_total`; Order totals in `ORDERS` | Persist the successful order-time values using integer VND and P1.5 allocation. Later price/Voucher changes never recalculate a placed Order. Reconciliation: `line_total = unit_price × quantity − allocated discount`; all allocated line discounts sum to the Order discount; `total_amount = subtotal − discount_amount + shipping_fee`; `PAYMENTS.amount = ORDERS.total_amount`. |
| Recipient/address | `ORDER_ADDRESSES` snapshot row | Copy recipient name/phone/province/district/ward/address line. Saving, editing or deleting a customer's `ADDRESSES` row cannot affect the snapshot. Shipping starts from this snapshot, not a subsequent address-book lookup. |
| Voucher | `ORDER_VOUCHER_SNAPSHOTS` | Preserve order-time normalized code/type/configured value and actual discount facts (including the allocated order/line discount represented by the approved schema). Later Voucher edits/status changes cannot affect history. Never infer the original discount from the current Voucher row. |
| COD Payment | `PAYMENTS` | One row per Order; copy full total and currency at placement, method `COD`, status `UNPAID`. Collection/refund actor/timestamps/reason are server-owned facts set only by their atomic commands. |
| Shipping | `SHIPPING_INFOS` | One row per Order, initially `PENDING`, recipient initialized from the Order snapshot. Mutable status/last-transition fields describe current manual shipping state; they are not an event timeline. |
| Transition history | `AUDIT_LOGS` | For each successful state-changing command, persist actor, action, entity ID, allowlisted before/after state, correlation ID where available and server timestamp in the same transaction. Never log credentials, tokens or raw secrets. No new Order timeline table or endpoint is implied. |

Do not hard-delete placed Order, OrderItems, Order address/Voucher/image snapshot, Payment, inventory ledger or audit history. Existing foreign-key/soft-delete rules remain authoritative. Snapshot stability is an API/query invariant; preserving only a URL that can later return different content is not sufficient for images.

## 5. API and DTO contract

These are target contracts, not a claim that current controllers already conform. Routes below use the documented `/api/v1` base.

| Method / route | Request / action | Response / effects | Authorization |
|---|---|---|---|
| `GET /api/v1/me/orders` | Pagination/filter fields already defined by the target API | `OrderSummaryDto[]` + pagination metadata | JWT; principal scoped |
| `GET /api/v1/me/orders/{orderId}` | No body | Customer Order detail from snapshots, Payment and ShippingInfo | JWT; owner only |
| `GET /api/v1/admin/orders` | Filter/page fields | `OrderSummaryDto[]` + pagination metadata | JWT + `ORDER_READ` |
| `GET /api/v1/admin/orders/{orderId}` | No body | `OrderDetailDto` with snapshots/current states and permitted actions | JWT + `ORDER_READ` |
| `POST /api/v1/admin/orders/{orderId}/actions` | `action`: `CONFIRM`, `START_PREPARING`, `DISPATCH`, `MARK_DELIVERY_FAILED`, `RETRY_DELIVERY`, `CANCEL`; optional documented reason/carrier/tracking fields only | Updated `OrderDetailDto` or the existing mutation-result envelope; one transition per request | JWT + `ORDER_EDIT` |
| `POST /api/v1/admin/orders/{orderId}/payment-actions` | `action=COMPLETE_DELIVERY_AND_COLLECT_COD`; no client actor, collection time, payment amount or currency | Updated order/payment/shipping summary; atomic `SHIPPING → COMPLETED` | JWT + `ORDER_PAYMENT` |
| `POST /api/v1/admin/orders/{orderId}/after-sales` | `action=RETURN_AND_REFUND_FULL`, required nonblank `reason`; no refund amount or per-item quantities | Updated Order/Payment summary; atomic `COMPLETED → RETURNED` + full COD refund record | JWT + `ORDER_AFTER_SALES` + `ORDER_PAYMENT` |

`PATCH /api/v1/me/orders/{orderId}/recipient` is **not a target v1 command** because `ORDER_ADDRESSES` is an immutable snapshot after placement. Do not wire this legacy route to mutate the snapshot. Customer order read routes remain account-scoped.

### DTO invariants

- `OrderSummaryDto`: `id, order_number, status, total_amount, currency, placed_at`.
- `OrderItemDto`: `id, product_id, sku_snapshot, product_name_snapshot, attribute_snapshot, image_url_snapshot, quantity, unit_price, discount_amount, line_total`.
- `OrderAddressDto`: `recipient_name, recipient_phone, province, district, ward, address_line` from `ORDER_ADDRESSES`, not current `ADDRESSES`.
- `OrderVoucherSnapshotDto`: order-time voucher facts and actual discount, not a live Voucher projection.
- `PaymentDto`: `method, payment_status, amount, currency, collected_by_account_id, collected_at, refund_amount, refunded_by_account_id, refunded_at, refund_reason`. Hide internal actor fields unless the caller is permitted to read them.
- `ShippingInfoDto`: `shipping_status`, existing manual recipient/carrier/tracking fields and available timestamps; no invented event list.
- Client requests must not supply `account_id`, actor IDs, state values except allowlisted action, trusted timestamps, stock deltas, unit prices, discounts, totals, `refund_amount`, or per-item return quantities. The server derives actor/time/money and controls all state transitions.

## 6. Stable errors and retries

Use the existing common error envelope; include a stable `code` and a safe message. Never expose SQL/constraint internals or another Account's Order.

| HTTP | Code | Meaning / retry rule |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Unknown action, malformed fields or missing required refund/cancellation reason. Correct the request; no write. |
| 401 | `UNAUTHENTICATED` | Missing/invalid token. |
| 403 | `FORBIDDEN` | Actor lacks the required capability. |
| 404 | `ORDER_NOT_FOUND` | No Order visible in the caller's scope; do not disclose a foreign Order's existence. |
| 409 | `ORDER_TRANSITION_NOT_ALLOWED` | Current state does not permit the requested transition, including retry after a transition already committed. No second side effect. |
| 409 | `INVENTORY_INSUFFICIENT_STOCK` | Confirmation's guarded quantity check failed; Order remains `PENDING`, and no stock/Order/audit subset commits. |
| 409 | `INVENTORY_SOURCE_ALREADY_APPLIED` | Conflicting duplicate semantic stock source; do not post a second movement. A legitimate committed cancellation/transition is resolved from the locked Order state. |
| 409 | `PAYMENT_NOT_COLLECTIBLE` | Order/ShippingInfo is not at the delivery-completion precondition or Payment is not `UNPAID`. |
| 409 | `PAYMENT_ALREADY_COLLECTED` | Collection has already committed. Do not collect twice. |
| 409 | `PAYMENT_NOT_REFUNDABLE` | Order is not `COMPLETED` with Payment `PAID`, or the whole-order return conditions are not met. |
| 409 | `PAYMENT_ALREADY_REFUNDED` | A full refund already committed. Do not issue another refund. |
| 409 | `REFUND_NOT_SUPPORTED` | Request attempts partial refund, a refund amount or multiple-refund behavior outside v1. |
| 409 | `ORDER_CANNOT_CANCEL_AFTER_DISPATCH` | Order is `SHIPPING`/delivered; a shipping failure must be registered before cancellation is eligible. |

### Retry and concurrency rules

1. `Idempotency-Key` plus the SHA-256 semantic fingerprint applies to **Order creation only**, as P1.6 specifies. Do not reuse the creation key for later actions, and do not invent a generic command-key table.
2. Transition commands lock and re-read the Order within the transaction before checking the precondition. A simultaneous loser sees the new committed state, fails with the appropriate transition/payment conflict and produces no duplicate business effect.
3. A retry after a lost response may return a deterministic `409` because the transition has already committed. That is acceptable for post-create actions: the contract guarantees **no duplicate effect**, not response replay for a command without a persisted command-id. Clients should re-fetch the Order after such a conflict.
4. Source-derived keys/unique constraints in `INVENTORY_TRANSACTIONS` independently prevent duplicate stock movement even if a caller uses a different request/correlation key. Cancellation must reference the exact original `ORDER` movement.
5. Successful state-changing commands write audit in the same transaction. If any Order, Payment, ShippingInfo, Voucher, Inventory balance/ledger or required audit operation fails, roll back every write in that command. Rejected/replayed-invalid commands do not mutate business state.

## 7. Transaction boundaries and locking

| Command | Required atomic write set |
|---|---|
| Create Order | P1.6: Order + OrderItems/snapshots + Order address/Voucher snapshot + COD Payment `UNPAID` + ShippingInfo `PENDING` + Cart consumption + eligible Voucher increment + audit. No Inventory movement at placement. |
| Confirm Order | Order `PENDING → CONFIRMED` + every negative `ORDER` movement + inventory balance/version update + required audit. The owning Inventory service validates current stock and source deduplication. |
| Cancel Order | Order/ShippingInfo `CANCELLED` + exact linked stock reversal for each existing order deduction (none if no deduction) + one-time Voucher quota release if a consumed Voucher exists + audit. |
| Prepare/dispatch/failure/retry | Order + ShippingInfo current-state/timestamp changes + audit; no inventory or Payment change. |
| Complete delivery / collect COD | Order `COMPLETED` + ShippingInfo `DELIVERED` + Payment `PAID` and collector/time + audit. |
| Return / refund full | Order `RETURNED` + Payment `REFUNDED`, full amount, actor/time/reason + audit. No inventory or Voucher mutation by default. |

Within a business transaction, lock the Order row first; then its OrderItems in stable order; then the one-to-one Payment and ShippingInfo rows in a consistent order; any inventory balances are locked in ascending `product_id` order through P1.4's owning service. Use guarded conditional transitions/row counts. Never have two application paths acquire these resources in inconsistent order. A transition cannot commit without the matching Payment/Shipping status changes and required audit.

### Inventory and Voucher compensation

- Inventory is deducted exactly once by `PENDING → CONFIRMED`, not by `COMPLETED` and not by placement. On eligible cancellation after deduction, use positive `ORDER_CANCEL_REVERSAL` movement(s), each tied to the original negative movement; never edit/delete the ledger. Cancellation before confirmation does not change stock.
- `DELIVERY_FAILED` and retry do not change stock. A returned/refunded Order does **not** automatically restock. The target has no persisted return inspection/return-line quantities; do not infer sellability or quantity from status alone. A future return-restock workflow needs explicit contract approval that fits the existing inventory source fields or a formal ERD amendment.
- An eligible cancellation releases a previously consumed Voucher use once within the cancellation transaction. The locked Order's single transition to `CANCELLED` is the guard against repeated release; P1.5 owns the guarded quota decrement. Refund/return does not release Voucher usage by default.
- A successful full refund must be a staff-recorded offline COD refund. No remote money movement or gateway retry occurs in this system.

|---|---|---|---|

| Shipping | `SHIPPING_INFOS` one-to-one with Order and existing status/manual fields | Current shipping status and latest available transition timestamps; audit keeps transition facts. | Carrier integration, callback log, tracking-event history or shipping-event table. |

The approved ERD and physical dictionary may contain fields beyond the summary above; only existing target fields may be used. If an action requires data not represented by the approved schema (for example, per-line return quantities or durable refund-attempt history), reject the scope expansion instead of introducing undocumented columns/tables.

## 9. Acceptance gate and non-goals

P1.7 documentation acceptance requires that: every allowed transition has actor, preconditions and atomic side effects; illegal transitions/retries are typed; the COD Payment and ShippingInfo state matrices reconcile with Order; snapshots survive mutable Product/address/Voucher changes; inventory deductions/reversals are linked and once-only; Voucher release occurs once only on eligible cancellation; full COD refund is capped at one; and no undocumented return/gateway/timeline persistence is claimed.

P3.10 runtime acceptance must exercise all transitions and forbidden edges, account isolation, insufficient-stock rollback, concurrent confirm/cancel, duplicate collection/refund, lost-response retries, one-time stock reversal/Voucher release, audit failure rollback, and snapshot reads after Product/attribute/image/address/Voucher edits. Schema-only or documentation checks do not prove runtime acceptance.

Not included: Java/service/controller lifecycle implementation, frontend state/action implementation, DDL/Flyway/seed changes, payment gateway, carrier integration, partial/multiple refund, item-level return/exchange, automated restock, new event/timeline tables or retention-policy changes.
