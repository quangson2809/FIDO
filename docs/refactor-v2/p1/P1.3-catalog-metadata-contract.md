P1.3 owns the meaning of Product ID, parent-child, SKU, row-owned Product fields, attribute definitions/options/values, catalog metadata and current Product images. P1.4 defines stock movement mechanics while using Product ID; P1.5 owns price/discount formulas and voucher rules; P1.6 owns Cart/quote; P1.7 owns Order lifecycle and snapshot writing; P1.8 owns long-term deletion/retention policy. ## 2. Product identity, hierarchy and field ownership

### 2.1 Identity and parent-child structure

- PRODUCTS.id is the only target catalog/sale-unit identifier. A grouping parent and each child are ordinary Product rows with distinct Product IDs. Cart, OrderItems, GoodsReceiptItems, inventory balances and inventory transactions refer to Product IDs, never a variant/option-combination ID.
- v1 allows one parent-child edge. A top-level Product has parent_product_id = NULL; a child references an existing top-level Product. A child cannot itself have children. Reject self-parenting, cycles, missing parents and any update that would make depth greater than one. The owning Product service must protect concurrent hierarchy mutations.
- Child Products are created explicitly through the Product resource with parent_product_id. Attribute values never auto-create a child, variant, SKU or saleable combination. No combination signature or generated-variant table is part of the target.
- Parent and child are independently sellable. Each row owns its own SKU, required selling price, status and inventory relationship. A parent's price/stock is not an aggregate of its children; a child's price/stock is not inherited.

### 2.2 SKU, price, stock ownership and NULL

- SKU is required and unique across all PRODUCTS rows, including parents and children. The API rejects blank or duplicate values and the database unique constraint remains authoritative. Do not construct SKU from size, color or any attribute combination.
- selling_price is required, stored as a non-negative whole-VND integer, and belongs to that Product row. It is not nullable, fractional, inherited or a per-variant override. P1.5 owns discount and order-total formulas; this contract defines the catalog selling-price field only.
- cost_price is nullable and exposed only to authorized administration. Monetary fields use integer VND, not floating point or decimal money values.
- Stock is not stored as a variant quantity on the Product DTO. Target inventory identity is (warehouse_id, product_id); a parent Product and each child have separate Product-ID stock balances. P1.4 owns balance/ledger mechanics.
- No field has implicit inheritance. Each row resolves its own name, slug, description, category_id and brand_id. A stored NULL remains NULL; it does not invoke a parent fallback. category_id and brand_id are nullable in the approved physical target: NULL means unassigned/unbranded, not “use parent value.” A child may have its own category/brand reference.
- Product status is DRAFT, ACTIVE, INACTIVE or ARCHIVED; deleted_at is a separate soft-delete marker. Public catalog queries must not conflate status with deletion. The approved target schema, not the legacy entity, defines field nullability.
- Product IDs are server-generated; create/patch requests cannot supply a chosen Product ID. Patch fields omitted from the request retain current values. Explicit null is accepted only for nullable fields; clearing a nullable reference never triggers fallback.

### 2.3 Category and Brand semantics

- Category and Brand are independent catalog references, not sale-unit identifiers. Their IDs are server-owned and stable. Category and Brand slugs are unique under target SQL; the ERD does not declare Category/Brand names unique.
- Category hierarchy may have multiple levels but must be acyclic. Do not apply the one-level Product parent-child restriction to Category.
- Product category/brand references are validated against their own rows. If NULL, the Product remains unassigned/unbranded. Do not fill from the parent or from a default reference.
- Category/Brand lifecycle and referenced-row deletion follow the approved catalog lifecycle/FK contract; detailed long-term deletion policy belongs to P1.8.

## 3. Typed attributes, options and values

### 3.1 Allowed model

- ATTRIBUTE_TYPES is a controlled lookup for exactly four value kinds: OPTION, TEXT, NUMBER and BOOLEAN. It is not a public arbitrary-type registry; no API creates new type kinds.
- An Attribute belongs to one AttributeType and has a stable unique code, display name, is_required, informational is_variant_defining and non-negative sort_order.
- An Option belongs to exactly one Attribute. Its value is unique within that Attribute; label is display text. Attribute/Option IDs are server-generated. Never accept an option from a different Attribute.
- A Product has at most one PRODUCT_ATTRIBUTE_VALUES row for each (product_id, attribute_id). Exactly one compatible value is populated: option_id for OPTION, text_value for TEXT, number_value for NUMBER, or boolean_value for BOOLEAN. The other three columns must be NULL. NUMBER follows target DECIMAL(18,4) descriptive-value representation; it is not an application money field.
- The stored value must match the referenced Attribute's current type. For OPTION, option_id must belong to the same attribute_id, enforced by service validation and the target composite FK.
- is_required=true means a Product must have a valid typed value before activation/publication. Draft Products may be incomplete. Turning requiredness on is rejected until existing ACTIVE Products satisfy it; do not silently backfill an inherited value.
- is_variant_defining is informational only. It neither changes Product ID/SKU nor generates a Product, variant, attribute-combination row or inventory record.
- Attribute code and type are stable after creation. Updating an Attribute or Option must not silently reinterpret existing Product values. Option machine value is immutable through the patch contract; label/order may change without changing Product identity. Attribute/Option deletion and long-term lifecycle rules are deferred to P1.8; this phase does not invent retention durations or deletion exceptions.

### 3.2 Metadata and filter contract

- Public GET /api/v1/catalog/meta returns product-facing metadata for catalog filter controls. Admin GET /api/v1/admin/catalog/meta returns authorized management metadata and requires CATALOG_READ.
- Metadata includes type IDs/codes/names, Attribute ID/code/name/type, requiredness and display order, plus nested Option ID/value/label/order. Sort Attributes by sort_order ASC, id ASC; Options by sort_order ASC, id ASC. Never infer options from Product variants or return legacy SizeSystem/Color as target Attribute types.
- Product listing filters are type-checked against metadata: OPTION uses a value owned by that Attribute; TEXT/BOOLEAN use typed equality; NUMBER accepts lower/upper bounds. Query syntax is attribute_filters[ATTRIBUTE_CODE]=value for OPTION/TEXT/BOOLEAN and attribute_min[ATTRIBUTE_CODE] / attribute_max[ATTRIBUTE_CODE] for NUMBER. Unknown codes, invalid type/operator combinations and conflicting duplicate bounds are validation errors. Predicates for different Attribute codes combine with AND. is_variant_defining does not govern filtering or generation.
- Metadata reads do not expose arbitrary type-creation APIs. Attribute and Option management routes are specified in §5; deletion routes are excluded until P1.8 defines lifecycle behavior.

## 4. Product image, primary image and order snapshot

- An image belongs to one Product through product_id. Gallery positions are non-negative, unique and contiguous from zero. Read order is sort_order ASC, id ASC for deterministic handling.
- The primary-image invariant is unified: an empty gallery has no primary; a non-empty gallery has exactly one primary, the image at sort_order = 0. Upload, remove and reorder update sort_order and is_primary atomically. No response may identify a different primary image from the first gallery image.
- Image upload/removal/reorder requests are scoped to the Product in the route. Reject image IDs owned by another Product, duplicate/gapped positions and invalid positions. Validate the complete reorder request before mutation; persist the full order and primary designation atomically. Concurrent mutations must not create duplicate positions or multiple/no primary images.
- image_url must resolve to stable immutable object/version content suitable for an Order snapshot; a mutable URL alone is insufficient if the underlying content can be overwritten. Current Product, Cart and quote projections read the current primary image. Order placement captures the selected image reference in ORDER_ITEMS.image_url_snapshot; later gallery edits do not rewrite that snapshot.
- P1.7 owns Order writes and historical snapshot DTOs. P1.8 owns retention duration and deletion/anonymization policy. Numeric retention remains TBD; do not schedule purging or remove content referenced by history until the policy is approved.
- Physical alignment decision resolved in P1.9 after owner approval on 2026-10-25: the isolated clean-reset target DDL defines `UNIQUE (product_id, sort_order)` as `uq_product_images_product_order`, and the Data Dictionary references the same index. The unique index prevents duplicate positions but cannot enforce continuity. Every upload/remove/reorder command must still lock or serialize mutations per Product and atomically maintain positions `0..n-1` plus `is_primary = (sort_order = 0)`. Before applying this constraint to any pre-populated database, check and repair duplicates, gaps and primary-image mismatches in an approved migration. P1.9 does not modify a live database or activate the clean-reset Flyway location.

## 5. Target API/DTO contract

Routes below specify target behavior; they are not implemented by this phase.

| Resource | Target request/response rules |
|---|---|
| GET /api/v1/catalog/products | Product-ID summaries; category/brand filters and typed Attribute filters per §3.2; deterministic paging. |
| GET /api/v1/catalog/products/{productId} | ProductDetailDto with row-owned Product fields, attribute values and ordered image gallery; never requires variantId. |
| GET /api/v1/catalog/meta | Product-facing metadata for filter controls; stable Attribute/Option ordering. |
| GET /api/v1/admin/catalog/meta | Admin metadata read with CATALOG_READ; returns four allowed types, Attributes and nested Options. |
| GET /api/v1/admin/products and GET /api/v1/admin/products/{productId} | Admin summaries/details use Product IDs, parent_product_id and typed attribute values; no variant subresource. |
| POST /api/v1/admin/products | Creates one Product row. A child is created by explicitly setting parent_product_id. Required SKU and whole-VND selling_price; no variants[] or generated combinations. |
| PATCH /api/v1/admin/products/{productId} | Omitted fields retain values; explicit null only for nullable fields. If attribute_values is supplied, it is a complete replacement set; invalid hierarchy/type/requiredness changes are rejected. |
| POST /api/v1/admin/products/{productId}/images | Upload into that Product gallery. First image becomes primary/order 0; subsequent image receives the next position unless a full reorder is requested. |
| DELETE /api/v1/admin/products/{productId}/images/{imageId} | Detach only an image belonging to the Product; renumber the remaining gallery and promote its first image atomically. Does not authorize deletion of object/version content needed by Order history. |
| PATCH /api/v1/admin/products/{productId}/images | Full reorder with image IDs and zero-based contiguous positions. Primary is derived from position 0, not a separate independent choice. |
| POST/PATCH Category and Brand routes | Validate reference fields and their own IDs; Product references remain nullable and row-owned. |
| POST /api/v1/admin/catalog/attributes | Create Attribute with attribute_type_id, code, name, is_required, is_variant_defining and optional sort_order. No client ID. |
| PATCH /api/v1/admin/catalog/attributes/{attributeId} | Update name, requiredness, informational flag or ordering. Code/type immutable. Enabling requiredness checks existing ACTIVE Products. |
| POST /api/v1/admin/catalog/attributes/{attributeId}/options | Create an Option under the path Attribute with unique value, label and optional order. |
| PATCH /api/v1/admin/catalog/attributes/{attributeId}/options/{optionId} | Option must belong to path Attribute. Update label/order only; attribute_id and machine value immutable. |
| AttributeType writes / Attribute or Option DELETE | No API defined here: types are controlled lookup values and deletion/lifecycle belongs to P1.8. |

### Shared DTO and validation rules

- Product requests/responses use id, parent_product_id, category_id, brand_id, name, slug, sku, description, selling_price, cost_price (admin only), status, attribute_values[] and images[] as permitted by role. Monetary values are integer VND.
- ProductAttributeValueDto contains attribute_id and exactly one of option_id, text_value, number_value, boolean_value. Reject unknown Attributes, option/type mismatch, cross-Attribute ownership, multiple/zero values, invalid NUMBER precision/range and missing required values when activating a Product.
- ProductImageDto contains id, image_url, is_primary and sort_order. A non-empty gallery has exactly one primary image at sort_order zero.
- Category/Brand create/patch validate required name/slug/status fields, target slug uniqueness, reference existence, Category self-parent/cycle and omitted-vs-null behavior. Product fields are validated against target DDL rather than legacy JPA nullability.
- Mutations use the existing global API envelope and stable validation/conflict errors. Never accept client-selected IDs.
