# P1.6 — Cart and Checkout Contract

**Disposition: CONTRACT SPECIFIED; runtime acceptance is pending P3.8/P3.9.** This phase changes documentation only. It does not claim legacy Cart/Checkout implementation already conforms.

## 1. Authority and ownership

- Owner-approved A-03: persisted Cart and order placement require authentication. Guest identity, guest Cart/checkout/order lookup and guest-cart merge are out of scope.
- Owner-approved DB-05: quote is stateless/advisory; order creation reloads and reprices server state; the idempotency namespace is account-scoped; a canonical SHA-256 request fingerprint is persisted with the Order; committed same-payload retry replays; changed-payload retry conflicts; concurrent duplicate requests cannot duplicate effects.
- P1.3 owns Product identity/status/current image. P1.4 owns Inventory mechanics. P1.5 owns whole-VND calculation, Voucher eligibility/quota and allocation. P1.6 owns Cart API/quantity semantics and order-create idempotency. P1.7 owns Order/Payment/Shipping lifecycle and transition timing. P1.8 owns retention/deletion policy.
- The approved 31-table ERD remains unchanged. No guest persistence, merge, one-active-Cart unique constraint, quote table, idempotency table or other schema addition is authorized here.

## 2. Account-scoped Cart policy

### 2.1 Current Cart selection (fail-closed)

1. The Account scope comes only from the authenticated principal. A client must not select another Account with `account_id` or `cart_id`.
2. The current Cart is the sole row owned by that Account with `status=OPEN`. `updated_at` is not a selection rule.
3. If there is **exactly one** OPEN Cart, use it. If there is **no** OPEN Cart, `GET /cart` returns `CartDto(id=null, items=[], subtotal=0)` without writing; a Cart-mutating command may create a Cart within that command's transaction. If there are **multiple** OPEN rows, return `409 CART_SELECTION_AMBIGUOUS` without writing, selecting, merging, deleting or changing any of them. This fail-closed behavior avoids inventing which cart the Account intended. Repair of anomalous rows is an explicit administrative/data-repair task, not a read-side effect.
4. P3.8 must serialize per-Account Cart creation/mutations under a consistent lock and verify the invariant before commit so normal runtime creates at most one OPEN Cart per Account. The existing schema does not enforce this by uniqueness; P1.6 does not add a constraint.
5. Cart status is server-owned. OPEN is mutable. CHECKOUT, if used during order creation, is transaction-local and must not remain committed after a failed operation. A successful Order-creation transaction consumes the selected Cart by deleting its working CART_ITEMS and moving the Cart to COMPLETED atomically with the Order write set. Any failure rolls back Cart consumption, leaving it OPEN with its original lines. A later add may create a new OPEN Cart. ABANDONED is not assigned by a public operation or an unapproved timeout rule.
6. `DELETE /cart` clears all lines of the sole OPEN Cart but keeps the Cart row and OPEN status. If no OPEN Cart exists, it returns the empty view without creating a row. It never changes stock, Voucher usage, Orders or order snapshots.

### 2.2 Cart operations and quantities

| Operation | Target semantics | Errors and invariants |
|---|---|---|
| `GET /cart` | Read the current OPEN Cart and server-derived subtotal; no OPEN Cart returns empty CartDto without a write. | JWT required. Multiple OPEN carts => `409 CART_SELECTION_AMBIGUOUS`; no foreign rows are exposed. |
| `POST /cart/items` | Request: `product_id, quantity`. Quantity is a positive SQL INT. Add quantity to an existing same-Product line; insert a line only if absent. It is additive, not a replacement/upsert-to-exact-value. If no OPEN Cart exists, create one and add the line atomically. Return resulting CartDto. | Product must exist, be non-deleted and ACTIVE. Combined quantity must fit `1..2,147,483,647`; reject overflow. Serialize concurrent same-Product adds and enforce unique `(cart_id, product_id)`. |
| `PATCH /cart/items/{cartItemId}` | Request: `quantity`, positive SQL INT. Replace the line quantity exactly; do not add it to the existing quantity. Return resulting CartDto. | The line must belong to the sole current OPEN Cart. Absent, foreign or non-current line => `404 CART_ITEM_NOT_FOUND`. Reject invalid quantity, non-sellable Product and out-of-range values. |
| `DELETE /cart/items/{cartItemId}` | Remove exactly one line in the selected current Cart. Return resulting CartDto. | Absent, foreign or non-current line => `404 CART_ITEM_NOT_FOUND`. No other Account/Cart may be changed. |
| `DELETE /cart` | Delete all lines from the selected current OPEN Cart; preserve its row and OPEN status. Return empty CartDto. | No OPEN Cart returns empty view without a write; multiple OPEN carts => `409 CART_SELECTION_AMBIGUOUS`. |

Common rules:

- No guest Cart, guest session, guest/account merge, `variant_id`, option-combination identity or client-selected Cart ID is part of the target API.
- Cart quantity expresses customer intent, not a stock commitment. Cart mutations never reserve or deduct stock. If Product availability changes after add, keep the line and expose availability as advisory data; quote and order creation must revalidate and reject unavailable Products/insufficient stock.
- `product_id` is the sale-unit identity end-to-end. Parent and child are independent Product rows with their own SKU, price and inventory per P1.3.
- Cart and line mutation, unique-line enforcement, account scope and audit (where required) must be atomic. Cross-module writes call the owning module service; a failed command must not leave a partial Cart mutation.

## 3. Quote contract

### 3.1 Request

`POST /api/v1/checkout/quote` requires JWT and accepts the semantic fields below:

```json
{
  "recipient_name": "string",
  "recipient_phone": "string",
  "province": "string",
  "district": "string",
  "ward": "string",
  "address_line": "string",
  "voucher_code": "OPTIONAL_STRING_OR_NULL"
}
```

The six recipient/address fields are required, nonblank and obey the target Data Dictionary field limits. Normalize phone according to the Account/Address phone rules; trim outer whitespace from required text before validation. Omitted or explicit-null `voucher_code` means no Voucher. A supplied code is normalized by P1.5 (trim + uppercase); a blank supplied code is invalid.

Do not accept `account_id`, `cart_id`, line items, `product_id`/quantity arrays, `quote_id`, prices, discount, shipping_fee, total or client-authored stock/status data.

### 3.2 Advisory behavior

- Read the sole current OPEN Cart, current Product status/price/image and stock, current Voucher configuration/quota, and server-owned shipping inputs. P1.5 defines the arithmetic and Voucher eligibility.
- Quote is calculation only: no `CHECKOUT_QUOTES`, no `quote_id`, no reservation or token to submit later, no Cart mutation, no inventory movement, no voucher usage increment and no Order/Payment write.
- With no non-empty current Cart return `409 CART_EMPTY`; with multiple OPEN carts return `409 CART_SELECTION_AMBIGUOUS`. Invalid body/address returns `400 VALIDATION_ERROR`; Product/stock/Voucher conflicts use the stable contracts owned by P1.3/P1.4/P1.5.
- `CheckoutQuoteDto` returns item calculation details, integer-VND `subtotal`, `discount_amount`, `shipping_fee`, `total_amount`, per-line allocated discount/line total and applicable Voucher summary. It never contains `quote_id` or a commit guarantee.
- Quote is stale when underlying state changes. It is advisory information, not an optimistic lock, reservation or guarantee of the next Order total.

## 4. Order-create request and server revalidation

`POST /api/v1/orders` accepts the same recipient/address/Voucher body as quote and requires the `Idempotency-Key` HTTP header. It does not accept `quote_id`, `cart_id`, client-selected order lines, Account ID, unit price, subtotal, discount, shipping_fee or total. A quote request is not a precondition to place an Order.

Before creating an Order, the server derives Account scope, resolves/locks the current Cart, requires at least one line and reloads Product eligibility, prices, stock, Voucher state/window/minimum/global quota, recipient snapshot input and server-owned shipping values. Recalculate all money under P1.5; ignore any previously displayed quote or client totals.

The Order-placement transaction covers Order, OrderItems, immutable Order address/Product/Voucher/image snapshots, COD Payment set to COD/UNPAID, ShippingInfo set to PENDING, applicable Voucher counter, Cart consumption and required audit. It does **not** post an Inventory movement: P1.7 owns the later PENDING→CONFIRMED transition that revalidates and deducts stock, and any subsequent eligible cancellation reversal. Those later state transitions each have their own atomic write set. Call each owning module service and apply P1.4/P1.5/P1.7 semantics; if any required write in a command fails, roll back that command's full write set.

## 5. Idempotency protocol

### 5.1 Header

- `Idempotency-Key` is required on `POST /api/v1/orders` only. Header names are case-insensitive; key values are case-sensitive.
- Accept 1–128 ASCII characters matching `[A-Za-z0-9._~-]+`. Reject missing/empty/repeated or malformed header values with `400 IDEMPOTENCY_KEY_INVALID` (or `IDEMPOTENCY_KEY_REQUIRED` when absent). UUID values are recommended.
- A client creates one key per logical Order-create operation and reuses the same key and semantic body for retries. A distinct purchase uses a fresh key. The key is not in the JSON body and is not reused for post-create Order state actions; P1.7/P3.10 own those.
  
### 5.2 Canonical fingerprint

Normalize the request **before reading Cart state** and derive the fixed semantic object with fields `contract_version="checkout-v1"`, `recipient_name`, `recipient_phone`, `province`, `district`, `ward`, `address_line` and `voucher_code`.

- Normalize required text to Unicode NFC and trim outer whitespace; preserve internal whitespace. Normalize recipient phone to the canonical target phone representation. Normalize a supplied Voucher code under P1.5. Represent omitted/null Voucher code as JSON null.
- Deterministically serialize the fixed object using RFC 8785 JSON Canonicalization Scheme after field normalization. Compute lowercase hexadecimal SHA-256 over UTF-8 bytes and persist it as `ORDERS.request_fingerprint` (`CHAR(64)`).
- Exclude the raw idempotency key, JWT, Account ID in a request body (not accepted), Cart ID/lines, quote output, live prices, stock, Voucher quota, shipping calculation, generated timestamps and JSON transport formatting.
- The fingerprint represents semantic client input. Current Cart is server-side state: a retry of an already committed key/body must replay the original Order even though that Cart has been consumed or changed.

### 5.3 Stored key namespace

Persist `ORDERS.idempotency_key` as:

```text
decimal(authenticated_account_id) + ":" + lowercase_hex(SHA-256(raw_client_key))
```

This namespace is at most 85 characters for a 20-digit Account ID and fits target `VARCHAR(120)`. Do not store the raw client key or trust client-provided Account IDs. The unique `ORDERS.idempotency_key` plus `ORDERS.request_fingerprint` is the durable idempotency record; do not add an idempotency table.

### 5.4 Replay, conflict and concurrency

| Scenario | Required outcome |
|---|---|
| First request commits | Return `201 Created`, Order confirmation body and target `Location` header; persist key/fingerprint in the same transaction as all Order effects. |
| Same Account + same key + same normalized semantic request + committed Order | Replay the original confirmation without writes or side effects. Preserve original `201`, body and `Location`; add `Idempotency-Replayed: true`. Perform key lookup before Cart resolution/validation. |
| Same Account + same key + changed normalized semantic request | Return `409 IDEMPOTENCY_PAYLOAD_MISMATCH`. Never alter the original Order or perform new side effects. |
| Same raw key from another Account | Stored namespace differs; the other Account must not discover or replay the first Account's Order. |
| Concurrent same-key requests | At most one transaction commits. The loser rolls back all effects, then reads the winner by scoped key and replays or conflicts after comparing fingerprints. Resolve uniqueness races rather than returning an avoidable untyped 500. |
| Timeout/lost response after commit | Retry exact key and semantic body. Server replays the committed Order; no duplicate Order, Voucher consumption, Inventory effect or Cart consumption. |
| Request fails before a committed Order exists | No committed idempotency record or partial business effect remains. Retry the same key/body for the same logical attempt; use a fresh key for a different semantic request. |

The key/fingerprint remains attached to its Order for at least the Order's lifetime. A client must never reuse a committed key for a different purchase.

## 6. Stable error contract

| HTTP | Code | Meaning |
|---|---|---|
| 400 | `VALIDATION_ERROR` | Invalid request/address/quantity. Correct the request before retry. |
| 400 | `IDEMPOTENCY_KEY_REQUIRED` / `IDEMPOTENCY_KEY_INVALID` | Missing or malformed header. |
| 401 | `UNAUTHENTICATED` | Missing/invalid token; no guest fallback. |
| 404 | `CART_ITEM_NOT_FOUND` | Absent, foreign or non-current Cart line; do not disclose foreign details. |
| 409 | `CART_EMPTY` | Quote/Order needs a non-empty current Cart. |
| 409 | `CART_SELECTION_AMBIGUOUS` | More than one OPEN Cart exists; fail closed without merging or mutating any Cart. |
| 409 | `PRODUCT_NOT_AVAILABLE` | Cart Product is missing, inactive or not sellable at validation. |
| 409 | `INVENTORY_INSUFFICIENT_STOCK` | Current stock is below requested Cart quantity; Cart does not reserve stock. |
| 409 | `IDEMPOTENCY_PAYLOAD_MISMATCH` | Committed Order exists for this Account/key with another semantic request. |
| 422 | P1.5 Voucher error | Voucher is ineligible under P1.5; quote does not reserve eligibility/quota. |

Use the existing error envelope. Never expose SQL details, stored key namespace, fingerprint or another Account's Order ID.

## 7. Use-case and phase handoff

| Use case | Normative contract | Owner |
|---|---|---|
| Read current Cart | Account-scoped, exactly-one-OPEN selection, empty no-write result when absent, explicit ambiguity error, server-derived projection. | P1.6 contract; P3.8 runtime. |
| Add Product | Product ID, positive additive quantity, one line per Cart/Product, checked overflow, no stock reserve. | P1.6 contract; P3.8 runtime/tests. |
| Replace quantity | Positive exact replacement; not additive; scope and bounds enforced. | P1.6 contract; P3.8 runtime/tests. |
| Remove/clear | Current Cart only; clear preserves OPEN Cart; no stock side effect. | P1.6 contract; P3.8 runtime/tests. |
| Quote | Stateless advisory calculation, no ID/persistence/side effects; P1.5 arithmetic and current server state. | P1.6 request contract; P3.9 runtime/tests. |
| Create Order | Revalidate/reprice; account-scoped key/fingerprint; replay/conflict/concurrency; atomic write set. | P1.6 contract; P3.9 orchestration/database tests. |
| Actions after creation | Order/Payment/Shipping transitions, cancellation, return/refund and their stock/quota effects; not part of create key. | P1.7 contract; P3.10 runtime/tests. |

## 8. Acceptance and boundaries

**P1.6 documentation acceptance: CONTRACT SPECIFIED. Runtime acceptance remains pending P3.8/P3.9/P3.10.**

Documentation checks must verify: no guest/variant path; explicit add-vs-replace quantities; account-scoped current Cart and fail-closed ambiguity behavior; quote has no persisted identifier; header/key namespace/canonical fingerprint/replay/conflict/concurrency/retry defined; P3.8/P3.9/P3.10 ownership clear.

Runtime acceptance later requires Account isolation; current-Cart creation/multiple-OPEN handling; add/update/remove/clear races and overflow; zero Inventory mutation on Cart/quote; quote write set empty; same-key lost-response replay; payload mismatch; cross-account same-key isolation; concurrent winner/loser; and full rollback injection.

FAIL if target Cart relies on guest/variant identity, Cart changes stock, quote requires/persists `quote_id`, client totals are authoritative, or a committed retry duplicates an Order/side effect. Guest/merge, new persistence, quote-token persistence, or a different idempotency guarantee require explicit owner-approved scope change.

No Cart/Checkout Java service or frontend implementation is included in P1.6. No DDL, seed, database reset, pricing formula, Voucher policy or Order state machine is changed.
