# P1.8 — Operations and System-Seed Runbook Requirements

**Type:** operator requirements/checklist, not a reset script or execution log. This document contains no credentials and performs no operation by itself.

**Dependency gate:** P2.1 seed SQL work must not start until P1.9 has passed integration/consistency acceptance. P1.8 contract: [P1.8 Operations, Audit, Content/Report and Seed Contract](P1.8-operations-seed-contract.md). Canonical clean-reset boundary remains in [Clean Schema Reset Runbook](../../refactor/clean-schema-reset-runbook.md).

## 1. Safety preflight before any destructive database operation

- [ ] Confirm the exact repository commit, branch and environment profile.
- [ ] Record host, port, database name and connection target from protected configuration; do not infer the target from a generic/default environment variable.
- [ ] Prove that the database is a disposable local/development/test target with no real, shared or persistent business data.
- [ ] Verify P1.9 passed and that the candidate DDL, dictionary, ERD, seed manifest and contract checker reference the same approved target.
- [ ] Verify exact-SHA clean MySQL schema and seed checks are green before proceeding.
- [ ] If database identity, disposability, approvals or target SHA cannot be proved, **stop**. Never run a reset against an unknown database, production, staging or shared integration.
- [ ] Preserve required external backups/logs where the disposable environment policy requires them. A backup is not permission to reset an otherwise protected database.

## 2. Fresh-install/schema and seed verification

The clean-reset Flyway location remains isolated until application mappings and the relevant P2/P3 acceptance gates authorize its use. Do not activate it solely to make a fresh install happen.

- [ ] Start from an empty, newly provisioned isolated MySQL target; validate the approved 31-table ERD/DDL and apply migrations in their approved order through Flyway.
- [ ] Verify physical table/column/index/check/FK definitions against the canonical ERD and Data Dictionary. Record actual FK delete actions. Current DDL has no explicit `ON DELETE CASCADE`/`SET NULL`; P1.9 must resolve the disposable CartItems exception before any implementation relies on database cascade. Until then, delete working-data child rows explicitly before parent rows.
- [ ] Apply the approved system seed through Flyway. Do not execute seed SQL manually over an already-applied migration to repair state.
- [ ] Verify three system Roles by immutable code: `CUSTOMER`, `ADMIN`, `SUPERADMIN`; each seed state is `ACTIVE`.
- [ ] Verify the 16 permission codes listed in P1.8 exactly once on a fresh install. Verify unique code keys and that the manifest contains no credential/account records.
- [ ] Verify `SUPERADMIN` has a `ROLE_PERMISSIONS` relation to every seeded Permission. The grant set must be code-resolved; do not rely on fixed generated IDs.
- [ ] Compare all seeded Permission codes with the target API actor/permission matrix. `ORDER_PROCESS`, `ORDER_FULFILLMENT` and `ORDER_EXCEPTION` exist alongside `ORDER_EDIT` in the current manifest; P1.9 must resolve the route mapping before P2.1 SQL work begins.
- [ ] Verify that the seed does not create an Account, demo user, password, session, catalog, order, inventory balance, voucher usage or fixture data. Do not infer grants for `ADMIN` or `CUSTOMER`; P1.2 remains authoritative.
- [ ] Verify Flyway history records schema/seed migration application and that fresh-install repeatability holds. The seed's goal is a predictable fresh install, not manual rerun of a versioned migration.

## 3. SUPERADMIN bootstrap requirements

- [ ] Bootstrap the first privileged Account only through the approved provisioning mechanism using protected external secret/configuration. Do not add Account credentials to V2 SQL, fixture SQL, repository examples, README, tickets or this runbook.
- [ ] Hash the initial password immediately. Never log or echo it, the password hash, JWT, session/cookie, OTP, secret-store value or raw Authorization header.
- [ ] Resolve the seeded `SUPERADMIN` Role by immutable code, assign it in the same protected provisioning operation as the Account bootstrap and emit a redacted audit event.
- [ ] Verify the Account is `ACTIVE`, can authenticate through the approved route and receives the full current Permission catalogue. Confirm the last-SUPERADMIN invariant is protected against concurrent demotion/deactivation/deletion.
- [ ] Verify the bootstrap secret/configuration is disabled or removed from the runtime path after successful one-time provisioning according to the deployment's secret policy. Do not print the secret to prove this.
- [ ] If the application has not yet implemented a supported bootstrap mechanism, mark bootstrap acceptance **BLOCKED** and stop. Do not compensate with a hand-written SQL insert or a guessed hash.

## 4. Audit readiness/acceptance evidence

Runtime implementation belongs to P3.0 (write path) and P3.11 (read path). Do not mark those implementations accepted solely because the schema exists.

- [ ] Verify a representative successful privileged mutation produces an `AUDIT_LOGS` row with actor, stable action/entity identity, allowlisted before/after fields, propagated correlation ID and server timestamp.
- [ ] Verify the whole business transaction rolls back when the required audit write is forced to fail.
- [ ] Verify actor IDs are security-principal-derived; `actor_account_id=NULL` is limited to trusted system events.
- [ ] Verify redaction with known synthetic secrets/PII: no password/hash, access token, cookie/session, OTP, Authorization header, secret, signed URL, raw file bytes or unnecessary address/phone/email appears in logs, audit payloads, returned DTOs or error messages.
- [ ] Verify multiple records from one multi-module command share the correlation ID, while the ID cannot authorize, impersonate or replace an idempotency key.
- [ ] Verify audit rows are append-only through ordinary APIs and that `AUDIT_READ` is enforced at the backend. Query ordering/filter/pagination is deterministic and payloads are redacted before serialization.
- [ ] Verify admin audit query access is logged according to P1.8 without recursively logging each returned row.

## 5. Content/report readiness/acceptance evidence

- [ ] Public content lookup returns only `PUBLISHED` pages. Missing, `DRAFT` and `ARCHIVED` slugs return the same not-found behavior; public DTOs omit `updated_by` and admin metadata.
- [ ] Admin read requires `CONTENT_READ`; create/edit/status transitions require `CONTENT_WRITE`. Writes derive `updated_by` and `updated_at` server-side and commit content + required audit atomically.
- [ ] Validate slug normalization/uniqueness, title/content requiredness, public content sanitization and the approved DRAFT/PUBLISHED/ARCHIVED transition graph. Ordinary deletion uses ARCHIVED; no purge job is enabled.
- [ ] Report routes enforce `REPORT_READ` at the backend. Test inclusive from/to business dates as `Asia/Ho_Chi_Minh` half-open instant ranges, DAY/WEEK/MONTH bucket boundaries and zero-filled approved Order statuses.
- [ ] Verify report money against P1.5/P1.7 (integer VND, whole-Order refund semantics, shipping included according to the approved total, return adjustment applied to the original completion period). Do not invent partial-refund calculations or state-history data.
- [ ] Verify deterministic product-performance ordering, bounded limit, Product-ID aggregation, no dropped archived/soft-deleted Products with historical activity and no reliance on mutable current prices/Voucher configuration for historical metrics.

## 6. Deletion/retention preflight

- [ ] Apply the P1.8 deletion matrix: soft-delete Account; disable/soft-delete referenced catalog and operational entities where the target has a matching field/status; preserve placed Order/snapshots, Payment, inventory ledger and audit history.
- [ ] Keep Attribute/AttributeOption DELETE routes absent. The current target has no `status`/`deleted_at` fields; retain these rows and do not hard-delete them. Any future deletion capability requires an owner-approved ERD/schema amendment.
- [ ] Confirm hard-delete attempts blocked by business/history FKs return safe typed conflicts and never trigger a cascade into historical data.
- [ ] Confirm working Cart cleanup explicitly removes CartItems before Cart in one transaction. The target DDL has no `ON DELETE CASCADE`; do not rely on or add one without a separate approved schema change.
- [ ] Confirm no retention scheduler, TTL index/job, object-storage expiry rule or ad hoc purge is active for AuditLog, order image assets or personal/business history.
- [ ] Treat audit/image/personal-business numeric retention and legal anonymization exceptions as unresolved DB-12 blockers. A legal deletion request that cannot be completed under an approved rule must be escalated; do not improvise by modifying audit actors or historical snapshots.
- [ ] Retain evidence of MySQL FK inspection, seed manifest counts, privilege tests, secret scanning and exact-SHA workflow links. Do not store sensitive data in the evidence artifact.

## 7. Exit/stop conditions

**P1.8 contract acceptance** requires the policy and manifest to be complete and internally consistent, while explicitly retaining DB-12 retention/privacy blockers and the P1.9 FK/cascade integration item.

**P2.1 must not start before P1.9 PASS.** P2.1 must implement seed SQL only after that gate; P3.0/P3.11 must provide the audit/report/content runtime evidence assigned to their ownership. No database reset, seeding, bootstrap account creation or purge is implied by this documentation runbook.
