# P1.8 — Operations, Audit, Content/Report and Seed Contract

**Status: DOCUMENTATION CONTRACT SPECIFIED.** This phase freezes operational policy against the owner-approved 31-table ERD v2. It does not implement audit services, report/content services, seed SQL, schema migrations or scheduled retention jobs.

## 1. Ownership, authority and scope

- The canonical ERD and [P1 Data Dictionary](P1-data-dictionary.csv) define physical fields and relationships. The approved [owner decision record](P1-owner-approval-2026-10-23.md) and [decision log](P1-decision-log.md) define DB-09/DB-11/DB-12 defaults.
- P1.8 owns audit field/redaction/correlation policy; content and report use cases at business-contract level; lifecycle/deletion/FK policy; system-seed inventory/bootstrap requirements and the operator runbook.
- **It does not redefine authorization policy** owned by [P1.2](P1.2-account-address-rbac-contract.md) and [P1.2 role/permission matrix](P1.2-role-permission-matrix.csv). It documents the existing seed catalogue and defers role grants to the approved matrix and existing RBAC contract.
- P1.3 remains authoritative for Product images, immutable image object/version references and primary-image semantics. P1.5 remains authoritative for VND/calculation/Voucher rules. P1.7 remains authoritative for Order/Payment/Shipping states and revenue/refund treatment.
- P2.1 implements/validates the system-seed SQL. P3.0 owns audit-write implementation; P3.11 owns audit-read plus report/content backend implementation. P1.9 must integrate and resolve cross-artifact/DDL consistency before P2.1 may start.
- Do not add tables, fields, event streams, report snapshots, content revision history or a new audit subsystem. Keep the current 31-table target.

## 2. Audit schema and write policy

### 2.1 Existing target record

Use the existing `AUDIT_LOGS` fields exactly; this policy does not change physical schema.

| Field | Contract |
|---|---|
| `id` | Database-generated immutable identifier. Never client supplied. |
| `actor_account_id` | Derive from the authenticated security principal for a human/administrative action. NULL is permitted only for a trusted autonomous/system event. Never use a caller-supplied actor ID. Account soft-delete preserves attribution; audit actor references must not be deleted or rewritten to NULL merely to make hard deletion succeed. |
| `action` | Stable domain event code, uppercase `UPPER_SNAKE_CASE`, within VARCHAR(120). The owning domain defines its business-event vocabulary; codes must not silently change between releases. Avoid free-form request text. |
| `entity_type` | Stable entity code within VARCHAR(80), owned by the domain contract. Use a controlled value, not a Java class name or arbitrary input. |
| `entity_id` | String form of the affected target entity's stable ID within VARCHAR(100). Do not put phone, email, slug, access token, or other personal/secret data here. |
| `before_data` / `after_data` | Nullable JSON allowlist containing only fields required to explain the audited change. Store normalized before/after business state, not a serialized JPA entity, raw request, full response or entire database row. |
| `correlation_id` | Optional trace/workflow identifier within VARCHAR(120). Propagate one value across all domain writes in the same business command. It is not an actor identifier, authorization credential, idempotency key or substitute for one. |
| `created_at` | Server/database-owned TIMESTAMP(6); immutable. Never accept a timestamp from the client. Persist using the approved UTC convention. |

This is a field policy, not a schema migration. Do not add IP address, user-agent, tenant, request-body, before/after text, audit-retention or event-version columns without a separate approved ERD amendment.

### 2.2 Correlation and atomicity

- At the request boundary, accept a correlation value only after validation and log-safe normalization; limit it to 120 printable ASCII characters from `[A-Za-z0-9._:-]`. If absent or invalid, generate a server-owned opaque trace ID. Do not return secrets from correlation middleware.
- Propagate the same correlation value through all owning services participating in one command and all audit records emitted by that command. A background/system command generates its own correlation value.
- Correlation groups related events; it must never determine the actor, grant a permission, select an Account, or bypass P1.6 request-key/fingerprint rules.
- An audit event is required to commit in the same transaction as the business mutation when the domain contract requires audit. If the audit insert fails, roll back the entire protected write set. Never swallow the audit failure and report success.
- The audit system must not require recursively auditing its own audit-row insert. Admin audit queries are a separately identifiable sensitive read and must emit one access event for each authorized query/export operation. Do not recursively audit the audit-event insert or emit one extra event per returned row.
- Emit audit for successful mutations, not for rejected commands as if they had committed. Rejections may be security/operational telemetry in application logs, subject to the same redaction policy; they are not fake successful AUDIT_LOGS events.
- Do not log every anonymous content read or every ordinary report response by default. Audit privileged reads such as querying/exporting audit history and privileged administrative mutations.

### 2.3 Redaction and minimization

**Never store or return** plaintext passwords, password hashes, reset/verification secrets, OTP values, JWT/access or refresh tokens, cookies/session IDs, raw Authorization headers, secret-manager values, database credentials, signed URLs containing credentials, private keys, or raw uploaded file bytes in audit data, application logs or error payloads.

- Use an explicit per-command allowlist for `before_data` and `after_data`. Exclude credentials and unneeded PII even if they exist on the source entity.
- Record business identifiers, approved state/status changes, safe codes, relevant integer-VND values and the minimum non-sensitive fields needed for accountability. Do not dump a whole Order including recipient/address snapshot merely because the Order changed.
- For Account/address operations, include Account/Address IDs and the relevant non-sensitive changed-field names; do not duplicate full phone/email/address values unless the owning security/legal contract specifically requires them. That exception must be documented by the domain owner and still excludes secrets.
- For images, record Product/Image identifiers and action outcome; never record file bytes, signed query strings, upload credentials or private storage keys.
- Apply the same redaction to `GET /admin/audit-logs`: redact payload keys recursively before serialization and never allow a query/filter to bypass redaction.
- Error messages to clients contain stable typed codes and safe summaries only, never SQL constraint internals, stack traces, secret values or audit payload dumps.

### 2.4 Minimum events requiring an audit record

Each domain remains responsible for its exact event codes and business preconditions. At minimum, its contract and implementation must cover these successful operations:

| Domain | Mutation/action requiring audit | Owner contract |
|---|---|---|
| Account/RBAC | Staff-account create/update, role grant/revoke, Role create/update/deactivate, Permission create/update/delete, protected bootstrap and security-critical account status/soft-delete changes | P1.2 account/address/RBAC contract; last-SUPERADMIN and SUPERADMIN grant invariants must remain atomic. |
| Catalog/Product | Product/category/brand/Attribute/Option create or update, status/deactivation/soft-delete, image upload/detach/reorder | P1.3 Catalog contract; never audit the binary or signed image URL. |
| Voucher | Voucher configuration/status mutation, successful global quota consume and eligible one-time cancellation release | P1.5 and P1.7 define money, eligibility and release semantics. |
| Inventory/receipt | Receipt create/edit/confirm/cancel and authorized stock adjustment; each balance/ledger mutation | P1.4 defines source, sign, deduplication, reversal and transaction boundary. |
| Order/Payment/Shipping | Order placement, each allowed Order transition, cancellation compensation, COD collection and one full refund/return | P1.6/P1.7 define state, actor, snapshot, amount and atomic side effects. |
| Content | Content page create/edit, publish, unpublish-to-DRAFT, archive or restore | P1.8 §4. Business row update and audit commit together. |
| Audit administration | Audit log search/export/query operation when performed by an authorized staff actor | P1.8 §2.2; record query metadata, not the full result set. |

A domain does not need to audit each public read or every failed validation as a committed business event. Domain-specific requirements may add events but may not weaken these minimum mutation requirements.

### 2.5 Audit read access

- `GET /api/v1/admin/audit-logs` requires the already approved `AUDIT_READ` permission. No new role, permission or endpoint is invented here.
- Supported filters are actor ID, action code, entity type/ID and UTC time range, plus normal page/page_size pagination. Validate IDs/lengths/time bounds; ignore no unknown filters silently.
- Default stable ordering is `created_at DESC, id DESC`; page boundaries must be deterministic. Query by UTC instants and return the standard response/pagination envelope.
- `AuditLogDto` maps only `id, actor_account_id, action, entity_type, entity_id, before_data, after_data, correlation_id, created_at`. Apply redaction before serialization, including to historical rows written by older versions.
- Deny by default when the caller lacks `AUDIT_READ`; UI visibility does not replace backend authorization.

## 3. Content use cases and business semantics

The target has one `CONTENT_PAGES` table with `id, slug, title, content, status, updated_by, updated_at`; status literals are `DRAFT`, `PUBLISHED`, `ARCHIVED`. There is no content revision/history table, publication timestamp or delete-event table.

### 3.1 Use-case matrix

| UC | Actor / permission | Read/write scope | Preconditions and result |
|---|---|---|---|
| CONT-01 Read published content | Anonymous/public | Lookup one page by `slug` | Return only `PUBLISHED`. Missing, `DRAFT` and `ARCHIVED` are indistinguishable as 404 to avoid leaking draft existence. No public draft preview. |
| CONT-02 List/manage content | Staff with `CONTENT_READ` for read routes | Admin content list/detail across statuses | Return paginated `slug, title, status, updated_at` summaries; optionally full page detail. Do not infer permission grants from role names. |
| CONT-03 Create draft | Staff with `CONTENT_WRITE` | Create one content page | New page starts `DRAFT`; server generates ID, sets `updated_by` from principal and `updated_at` from server. Validate required slug/title/content and unique slug; insert and audit atomically. |
| CONT-04 Edit draft/published page | Staff with `CONTENT_WRITE` | Update allowed content fields | Omitted fields retain current values; fields not explicitly nullable cannot be cleared. A published edit changes the current page; it does not create a historical revision. Set editor/time server-side and audit before/after allowlisted values atomically. |
| CONT-05 Publish/unpublish/archive/restore | Staff with `CONTENT_WRITE` | Change only the allowed status transition | State graph: `DRAFT → PUBLISHED` or `ARCHIVED`; `PUBLISHED → DRAFT` or `ARCHIVED`; `ARCHIVED → DRAFT`. An archived page must return to DRAFT before republishing. Enforce current status under lock; update row and audit in one transaction. |
| CONT-06 Delete/purge content | Not an ordinary CRUD operation in this target | No public/admin hard-delete route is specified | Use `ARCHIVED` for ordinary removal. Numeric business-data retention is TBD; do not add an automatic or ad hoc purge. Any future hard-delete/legal-erasure path requires an approved retention/anonymization decision and explicit owner contract. |

### 3.2 Content validation and exposure

- `slug` is a stable URL key, 1–180 characters, normalized to lowercase ASCII words separated by single hyphens (pattern `[a-z0-9]+(?:-[a-z0-9]+)*`). Reject blank or malformed slugs and uniqueness conflicts; do not silently change a published slug because a title changed.
- `title` is required, trimmed/non-blank and limited to the schema's 255 characters. `content` is required and stored as TEXT. The UI/rendering layer must treat content as untrusted input, sanitize permitted markup and prevent script injection; do not render arbitrary raw HTML without a documented sanitizer policy.
- The target API contract uses `CONTENT_READ` for admin read and `CONTENT_WRITE` for create/update/state changes. This defines use-case boundaries only; P1.2 owns the role-grant policy and P2.1 owns system seed SQL.
- Public response exposes only published content fields needed by the site; it must not disclose internal `updated_by` account IDs or admin-only metadata. Admin DTO may include `updated_by` and `updated_at` to support accountability.
- There is no row-level history in `CONTENT_PAGES`. Audit captures approved before/after change summaries; it must not be presented as a version-management or rollback UI.
- Public reads and published-page lookup do not mutate content and do not consume a permission grant. A route must not return a draft/archived body when a caller merely supplies its slug.

## 4. Report use cases and data contract

The existing report routes require `REPORT_READ`. This section fixes query dimensions and data sources, but **P1.5 owns currency/Voucher arithmetic and P1.7 owns Order/Payment state and return semantics**. No report table, snapshot cache, event log or denormalized persistence is introduced.

### 4.1 Use-case and source matrix

| UC | Actor / permission | Target output | Approved read sources and basis |
|---|---|---|---|
| REP-01 Overview | Staff + `REPORT_READ` | `ReportOverviewDto(from, to, completed_sales, returned_adjustment, net_sales, orders_by_status)` | `ORDERS`, `PAYMENTS`, `SHIPPING_INFOS`. Sales/return amounts use P1.5/P1.7; status counts use current Order status and Order creation date. |
| REP-02 Sales trend | Staff + `REPORT_READ` | `SalesTrendDto`; per-period completed sales, returned adjustment, net sales | `ORDERS.total_amount`, `SHIPPING_INFOS.delivered_at`, `PAYMENTS` as corroborating current payment facts. Credit the gross completion in its completion period and the full whole-Order return adjustment in that same original completion period, per P1.7; do not move the adjustment to the later refund date. |
| REP-03 Orders trend | Staff + `REPORT_READ` | `OrdersTrendDto`; total orders and counts for every Order status per period | `ORDERS.created_at` and current `ORDERS.status`. Counts are current-state counts bucketed by creation date, not a historical state-transition timeline. Include every P1.7 status in each bucket, zero-filled where absent. |
| REP-04 Product performance | Staff + `REPORT_READ` | `ProductPerformanceDto`; Product ID, display name/thumbnail, completed/returned/net units | `ORDER_ITEMS` + `ORDERS` + `SHIPPING_INFOS`; `PRODUCTS` and current primary `PRODUCT_IMAGES` supply optional current display fields. Key metrics by Product ID; include archived/soft-deleted Products with historical activity. `completed_units` includes orders that reached completion (current status `COMPLETED` or `RETURNED`); `returned_units` sums all line quantity for current `RETURNED` Orders; `net_units = completed_units - returned_units`. In v1, `RETURNED` is a whole-Order return, so all line quantities count as returned. |
| REP-05 Filter, paginate and rank | Staff + `REPORT_READ` | Bounded, deterministic result | Validate date ordering and granularity; `limit` defaults to 10 and is 1–100. Product performance sorts by `net_units DESC, completed_units DESC, product_id ASC`. Do not provide arbitrary client-supplied SQL/group-by fields. |

### 4.2 Common date and aggregation rules

- `from` and `to` are inclusive business calendar dates in `Asia/Ho_Chi_Minh`. Convert the query to a half-open instant range `[startOfDay(from), startOfDay(to + 1 day))` in that timezone, then compare against stored timestamps according to the approved UTC/TIMESTAMP convention. Reject missing/malformed dates and `from > to`; never compute periods using the server host's local timezone.
- `DAY` periods start at local midnight. `WEEK` periods start Monday (ISO weekday) at local midnight; `MONTH` periods start on the first local calendar day. `period_start` and `timezone` in DTOs must describe these local reporting periods consistently.
- `completed_sales` sums the persisted gross Order total for Orders that reached completion (current status `COMPLETED` or `RETURNED`) in the original `SHIPPING_INFOS.delivered_at` completion period. `returned_adjustment` subtracts the full persisted Order total for current `RETURNED` Orders in that same original completion period, even if `refunded_at` falls in a later period; `net_sales = completed_sales - returned_adjustment`. Values remain whole VND and follow P1.5/P1.7; reporting does not recalculate Order money or shipping.
- A whole Order in `RETURNED` has a full refund under P1.7; do not invent partial-return allocations. Use the original completion period for returned adjustment even when `refunded_at` falls in a later period. Retain the immutable `SHIPPING_INFOS.delivered_at` completion timestamp.
- Status-count metrics describe the latest committed state of each Order at query time, grouped by its creation date. They are not a count of state transitions. Creating an event timeline or historical per-status-by-day table is out of scope.
- Trend buckets are continuous for the selected calendar range and missing counts are zero-filled. Product metrics group by `product_id` from order-time lines; use P1.7 whole-order-return semantics. Do not derive historical money/quantity from mutable Product price, current SKU, current images or Voucher configuration.
- Public/customer actors cannot read administrative reports unless the approved P1.2 role grant explicitly gives `REPORT_READ`. Hide report routes/links in UI where appropriate, but enforce the permission in the backend.

### 4.3 Report non-goals

No export job, spreadsheet/file endpoint, report snapshot table, materialized analytics schema, custom SQL filter, audit event stream, or historical status-transition report is implied. Performance optimization must not change the approved calculation, time boundary, current-state status basis, integer-VND arithmetic or deterministic ranking.

## 5. Retention and deletion/FK lifecycle matrix

### 5.1 Global rules

- DB-12 lifecycle/FK defaults were owner-approved on 2026-10-23. **Numeric retention duration for audit logs, immutable Order image content, and personal/business data remains TBD; legally required anonymization/deletion exceptions also remain TBD.** This is a blocker for automatic purge and for declaring retention/privacy fully frozen, not permission to choose a duration.
- Soft-delete Account. Soft-delete/disable Product, Category, Brand, Attribute/Option, Voucher and Warehouse where their target fields/status support it. Do not hard-delete records with operational or history references.
- Preserve posted Order, OrderItem, OrderAddress, OrderVoucherSnapshot, Payment, InventoryTransaction and AuditLog. Correct stock history with immutable compensating ledger rows; never edit/delete posted ledger history.
- RESTRICT is the default for business/history FKs. CASCADE is permitted only for explicitly disposable dependent working data such as CartItems. SET NULL requires a specifically approved optional-reference justification. Nullable by itself does not mean a reference should be nulled on deletion.
- **Physical-DDL caveat for P1.9:** current clean-reset `V1__clean_schema.sql` does not declare `ON DELETE CASCADE` or `ON DELETE SET NULL` for the reviewed FKs, including CartItems. Therefore MySQL's effective current FK behavior is restrictive. Until P1.9 makes and validates an explicit schema decision, code/runbooks must delete disposable children before parents in one transaction; do not assume CartItems cascade at database level.
- Ordinary CRUD/API must not hard-delete history to work around an FK. Fail closed and report a stable conflict when the reference/lifecycle policy blocks a deletion. This matrix is not an authorization to change the DDL in P1.8.

## 6. System seed and bootstrap specification

This is the normative **seed manifest**. The single isolated target baseline `backend/src/main/resources/db/clean-reset/V1__clean_schema.sql` contains all 31 target tables and the approved 13-code system seed in one Flyway version. Pre-release schema/seed edits update this baseline instead of adding a version per phase. The baseline remains isolated from the active runtime migration chain while the remaining entity mappings and acceptance gates are incomplete.

### 6.1 System role manifest

| Immutable `ROLES.code` | Seed state | Seed policy |
|---|---|---|
| `CUSTOMER` | `ACTIVE` | System role. Public registration assigns it server-side and atomically to the new Account. No implicit administrative permission grants. |
| `ADMIN` | `ACTIVE` | System role. No implicit business permissions by role name; business access comes only from explicit approved `ROLE_PERMISSIONS` grants. |
| `SUPERADMIN` | `ACTIVE` | System role. Its grants equal the full current Permission catalogue at seed time; runtime invariant keeps every current Permission granted and automatically grants newly created Permissions. At least one non-soft-deleted ACTIVE Account must hold it. |

The seed creates roles only; it does **not** create any Account, password, session, demo customer, initial SUPERADMIN credential or reusable fixture. Role IDs are generated by persistence and must be resolved by immutable code, never hard-coded numeric IDs.

Current legacy runtime policies/tests may still mention those codes and remain unaccepted legacy evidence until their implementation phase.

### 6.3 Required grant invariants

- At seed completion, `SUPERADMIN` has a `ROLE_PERMISSIONS` row for every seeded Permission. This grant set is derived by role/permission code, not fixed numeric IDs.
- Seed does not grant business/admin permissions implicitly to `CUSTOMER` or `ADMIN`. Exact grants for non-SUPERADMIN roles follow [P1.2](P1.2-account-address-rbac-contract.md) and its role matrix; P1.8 does not override that matrix.
- An authenticated Account receiving `CUSTOMER` is not allowed to self-select roles/permissions. Staff role assignments are explicit and authorized; an inactive Role cannot be newly assigned or contribute effective permissions.
- System roles `CUSTOMER`, `ADMIN`, `SUPERADMIN` and seed-manifest Permissions are protected from ordinary deletion. P1.2 owns custom Role/Permission deletion guards, grant replacement, and the last-SUPERADMIN concurrency invariant.
- IDs are generated. SQL must not embed production identity IDs, personal data, password hashes or secret values. Do not seed a SUPERADMIN Account with known credentials in migrations, repository examples or documentation.
- Flyway owns one-time installation. Repeatability means a verified fresh installation yields the exact role/permission/grant manifest; do not manually rerun an already-applied non-repeatable migration to “repair” seed state. Repair must use an approved forward migration/operation and preserve Flyway history.
- Development/test fixtures are a separate mechanism from the system seed. Fixture data must contain no real personal information, reusable plaintext credentials or privileged production-like account.

### 6.4 SUPERADMIN bootstrap and secret handling

- Bootstrap Account creation is an operational provisioning step, separate from V2 system seed. The password/secret must arrive through a deployment secret manager or protected environment configuration at runtime, not source control, Flyway SQL, README, runbook, issue text or chat.
- A designated bootstrap mechanism hashes the initial password immediately, creates/uses an `ACTIVE` Account, assigns the seeded `SUPERADMIN` Role atomically, and writes a redacted audit event. Do not insert plaintext credentials or hand-crafted password hashes directly with ad hoc SQL.
- Do not log secret values when configuration is absent/invalid. Validate the bootstrap operation's target environment and Account identity; fail closed if it cannot prove that the request is authorized and is not targeting persistent data by mistake.
- After bootstrap, verify the Account is `ACTIVE`, is assigned the seeded `SUPERADMIN`, receives the seed Permission set, can authenticate through the approved route, and that a second authorized SUPERADMIN remains protected during future changes. Remove/disable the bootstrap secret path after the one-time provisioning has completed according to deployment policy; never print the secret for confirmation.
- P2.1 owns SQL implementation; security/bootstrap code and tests must be assigned to the owning implementation phase. This document does not define a new HTTP endpoint or authentication flow.
