# P1.5 — Pricing and Voucher Contract

**Branch:** `docs/p1-5-pricing-voucher-contract`  
**Baseline:** `demo1` after P1.4, commit `7fddfc3e65916cad58134705e41782352f728e85`  
**Decision basis:** owner-approved DB-06 and DB-10, 2026-10-23. This phase freezes their target semantics; it does not implement pricing, voucher service, UI, seed SQL or Order transitions.

## 1. Ownership and authority

- The approved 31-table ERD and P1 Data Dictionary remain the physical schema authority. Money is stored as whole-VND integers; do not add decimal money fields, voucher-scope joins, per-account quota ledgers or other tables.
- P1.5 owns calculation semantics, voucher eligibility/configuration and the quota-consume/release operation when called.
- P1.6 owns Cart/quote/order-create request idempotency and replay transport. Quote is advisory; order placement revalidates all inputs.
- P1.7 owns Order/Payment state transitions and decides which cancellation transition invokes the voucher-release operation. P1.5 does not define Order transition timing, refund lifecycle or UI behavior.
- P3.6 implements arithmetic; P3.7 implements voucher/quota behavior; P3.9 orchestrates through owning services. The contracts here do not imply runtime acceptance.

## 2. Money representation and field meanings

### 2.1 Currency and precision

- v1 uses **VND only**. Every monetary request/response/storage/report value is a JSON integer in VND; do not serialize floating-point money or fractional VND.
- Monetary columns use the owner-approved BIGINT contract. Values representing prices, costs, shipping, subtotal, discounts, line/order totals, payment amounts and refunds are non-negative unless explicitly defined otherwise; all calculated values must fit signed BIGINT `0..9,223,372,036,854,775,807`.
- `VOUCHERS.discount_value` and `ORDER_VOUCHER_SNAPSHOTS.discount_value_snapshot` are type-dependent: FIXED means integer VND; PERCENT means integer basis points. They are not always monetary amounts.
- Use exact integer arithmetic and overflow-checked multiplication/summation. Never use binary floating-point to calculate money. If a line subtotal or an intermediate/result cannot fit the target storage range, reject the command before any commit.

### 2.2 Canonical calculation

For the accepted Order lines, using server-owned Product prices and positive quantities:

1. `line_gross_i = unit_price_i × quantity_i`.
2. `subtotal = Σ(line_gross_i)`; it is the merchandise total **before discount** and excludes shipping.
3. `discount_amount` is the single accepted order-wide voucher discount, or zero when no voucher is applied. No Product/Category-targeted or stacked voucher discount exists in v1.
4. `line_discount_i` is the allocated integer-VND share of `discount_amount`; `Σ(line_discount_i) = discount_amount`.
5. `line_total_i = line_gross_i − line_discount_i`.
6. `total_amount = subtotal − discount_amount + shipping_fee`.
7. `PAYMENTS.amount = ORDERS.total_amount`, `PAYMENTS.currency = ORDERS.currency = 'VND'`. In v1 `refund_amount` is zero or the full paid amount; P1.7 owns the permitted refund transition and timing.

Required reconciliation invariants:

- `subtotal = Σ(unit_price_i × quantity_i)`.
- `ORDERS.discount_amount = Σ(ORDER_ITEMS.discount_amount)` and `0 ≤ discount_amount ≤ subtotal`.
- If a voucher is applied, `ORDER_VOUCHER_SNAPSHOTS.discount_amount_snapshot = ORDERS.discount_amount`, and the snapshot records the exact discount type/value used. If no voucher is applied, the order discount is zero and no voucher snapshot is created.
- `ORDER_ITEMS.line_total = unit_price × quantity − discount_amount`, with `0 ≤ discount_amount ≤ unit_price × quantity` and `line_total ≥ 0`.
- `ORDERS.total_amount = subtotal − discount_amount + shipping_fee`, and `total_amount ≥ 0`.
- `shipping_fee` is a non-negative, server-owned integer-VND input; the recorded baseline is 30,000 VND unless an explicit server configuration overrides it. It is added after discount and is excluded from the voucher minimum-order check.
- Reports aggregate persisted Order/Payment snapshot amounts using integer VND. They must not recompute a historical Order from current Product or Voucher configuration. Report state inclusion/return accounting remains under the relevant Order/report contract; this phase does not invent an alternative revenue state machine.

## 3. Voucher calculation

### 3.1 Configuration and units

| Field | Contract |
|---|---|
| `code` | Trim leading/trailing whitespace and normalize to uppercase before uniqueness lookup/storage. Reject blank values and values over 80 characters. The normalized code is the redemption identity. |
| `discount_type` | Only `FIXED` or `PERCENT`. |
| `discount_value` | Required positive integer. FIXED = VND; PERCENT = integer basis points (bps), where 100 bps = 1%, 1,000 bps = 10%, and 10,000 bps = 100%. PERCENT is limited to 1..10,000 bps. |
| `minimum_order_value` | Non-negative integer VND. Compare against merchandise subtotal before discount and excluding shipping; equality meets the minimum. |
| `maximum_discount` | Optional non-negative integer VND cap. If present, cap the rounded candidate discount before the final subtotal bound. It is always VND, including for PERCENT vouchers. |
| `starts_at`, `ends_at` | Optional UTC instants. The valid redemption window is half-open: `starts_at ≤ now < ends_at`; NULL start/end means no bound at that side. If both are set, `starts_at < ends_at`. Capture one server `now` instant for eligibility evaluation. |
| `usage_limit` | Positive integer global cap, or NULL for unlimited uses. No per-account cap or usage ledger exists. |
| `usage_count` | Server-owned current quota occupancy: committed voucher uses not released by an eligible cancellation. Starts at zero; must satisfy `0 ≤ usage_count ≤ usage_limit` when a limit is configured. Client cannot set it. |
| `status` | Only `DRAFT`, `ACTIVE`, `INACTIVE`, `EXPIRED`. Only ACTIVE is potentially redeemable; window, minimum and quota are checked independently. EXPIRED is terminal for redemption. |

`maximum_discount` applies as a monetary cap after the percentage has been rounded (or after the fixed candidate is read); the result is then bounded by subtotal. A missing cap means no extra cap. An applied voucher must never produce an Order discount greater than subtotal.

### 3.2 Exact discount algorithm

Let `S = subtotal`:

- If no voucher is provided, `discount_amount = 0`.
- FIXED: `candidate = discount_value` VND.
- PERCENT: `candidate = ROUND_HALF_UP(S × discount_value_bps ÷ 10,000)` VND. For non-negative integers, implement exactly as `(S × discount_value_bps + 5,000) DIV 10,000`, using overflow-safe integer arithmetic.
- If `maximum_discount` is non-NULL, set `candidate = min(candidate, maximum_discount)`.
- Set `discount_amount = min(candidate, S)`. This bounds the discount even if a FIXED voucher is greater than subtotal. When `S = 0`, discount is zero and allocation performs no division. If the final calculated discount is zero (including after rounding or a zero cap), the voucher is not redeemable and its quota is not consumed.
- Eligibility uses `S ≥ minimum_order_value` before discount; shipping is not included in `S`.

Do not round each line independently. Calculate/round the order-wide voucher discount once, then allocate the integer result with the largest-remainder algorithm in §4.

## 4. Largest-remainder line allocation

For each OrderItem, let `G_i = unit_price_i × quantity_i` and `S = ΣG_i`:

1. If `discount_amount = 0`, allocate zero to every line. If `S = 0`, the discount must also be zero; allocate zero to every line.
2. Compute exact rational share `R_i = discount_amount × G_i / S` using integer numerator and denominator.
3. Set initial allocation `A_i = floor(R_i)` and remainder `r_i = (discount_amount × G_i) mod S`.
4. Compute `leftover = discount_amount − ΣA_i`. Add one VND to the `leftover` lines with the largest `r_i`; ties are resolved by ascending `product_id`.
5. The final allocation must sum exactly to `discount_amount`, and each allocated share must not exceed its line gross.

Target Cart identity is `(Cart, Product)`, so a normal Order has one consolidated line per Product ID. If a future contract permits duplicate Product lines, a stable secondary tie-break must be approved before implementation; do not rely on unspecified collection iteration order.

## 5. Worked examples (expected outputs)

### Example A — HALF_UP at exactly 0.5 VND

Two lines: Product 10 has `unit_price=2`, `quantity=1`; Product 20 has `unit_price=3`, `quantity=1`. `subtotal=5`. Voucher is PERCENT with `discount_value=1000` bps (10%), no maximum cap, minimum 0. The raw discount is `5 × 1000 / 10000 = 0.5`; HALF_UP produces **1 VND**.

| Product ID | Line gross | Exact proportional share of 1 | Allocated discount | Line total |
|---:|---:|---:|---:|---:|
| 10 | 2 | 0.4 | 0 | 2 |
| 20 | 3 | 0.6 | 1 | 2 |

`subtotal=5`, `discount_amount=1`, `shipping_fee=30,000`, `total_amount=30,004`, `PAYMENTS.amount=30,004`. Sum of line discounts is 1 VND.

### Example B — largest-remainder tie broken by Product ID

Three lines each have gross 10 VND, with Product IDs 30, 10 and 20. A FIXED voucher has `discount_value=1` VND. Each exact share is 1/3 VND; all remainders tie. The remaining VND goes to the lowest Product ID.

| Product ID | Line gross | Allocated discount | Line total |
|---:|---:|---:|---:|
| 10 | 10 | 1 | 9 |
| 20 | 10 | 0 | 10 |
| 30 | 10 | 0 | 10 |

`subtotal=30`, `discount_amount=1`, `shipping_fee=30,000`, `total_amount=30,029`. Input line order must not change this result.

### Example C — percentage, cap and amount reconciliation

Product 101: `unit_price=1,999`, `quantity=2`, gross 3,998. Product 205: `unit_price=999`, `quantity=1`, gross 999. Thus `subtotal=4,997`. Voucher is PERCENT `discount_value=1500` bps (15%), `maximum_discount=700`, and the minimum is satisfied.

- Raw discount: `4,997 × 1,500 / 10,000 = 749.55` VND; HALF_UP gives 750 VND.
- Apply the VND cap: `min(750, 700) = 700` VND.
- Largest remainder yields Product 101 discount 560 and line total 3,438; Product 205 discount 140 and line total 859.
- `Σ line discount=700`, `subtotal=4,997`, `shipping_fee=30,000`, `total_amount=34,297`, and `PAYMENTS.amount=34,297`.

### Example D — fixed discount cannot make total negative

With subtotal 8 VND and a FIXED voucher value 20 VND (no extra cap), final discount is `min(20, 8) = 8`, line total is zero, and with shipping 30,000 VND the order total is 30,000 VND. Negative line/Order totals are forbidden.

## 6. Eligibility, states and redemption API

A voucher is redeemable only when **all** conditions hold at the time the server evaluates order placement:

1. The normalized code resolves to a Voucher.
2. `status=ACTIVE` (DRAFT, INACTIVE and EXPIRED are rejected).
3. Current UTC instant is in `[starts_at, ends_at)` using the nullable-bound rules above.
4. Merchandise subtotal before discount is at least `minimum_order_value`.
5. `usage_limit IS NULL` or `usage_count < usage_limit`.
6. The Order has no other voucher/discount stack. No Product/Category allowlist, per-account usage cap or per-account usage ledger is supported.
7. The final calculated discount after rounding/cap/subtotal bound is greater than zero; a zero-value discount does not consume quota.

Administrative state intent is DRAFT→ACTIVE/INACTIVE, ACTIVE→INACTIVE/EXPIRED, INACTIVE→ACTIVE/EXPIRED; EXPIRED is terminal. An ACTIVE voucher outside its timestamp window is not redeemable even if stored status has not been refreshed to EXPIRED. Exhausted quota does not alter status and can become available again if an eligible cancellation releases a use.

Target admin endpoints:

| Method | Path | Contract |
|---|---|---|
| GET | `/api/v1/admin/vouchers` | Search/paginate canonical Voucher records; no per-account usage history. |
| GET | `/api/v1/admin/vouchers/{voucherId}` | Read one Voucher's configuration and global quota counters. |
| POST | `/api/v1/admin/vouchers` | Create a Voucher in DRAFT with `usage_count=0`; actor/ID/count are server-owned. |
| PATCH | `/api/v1/admin/vouchers/{voucherId}` | Patch allowed configuration/status fields. Usage counter is never client-writable; a new `usage_limit` cannot be set below current `usage_count`. Existing Order snapshots are unchanged by later edits. |

These are target API/DTO semantics, not runtime compatibility claims. Read/write access must use the permission defined by the RBAC/seed contract (P1.8); this phase does not create or seed permissions.

## 7. Quota consume and compensation contract

### 7.1 Consume

- Quote never increments or reserves quota. It may report current eligibility only; it is not a reservation.
- On successful Order placement with a Voucher, atomically claim one use by guarding the global counter: the row must still be ACTIVE, inside the configured time window, meet the minimum subtotal and have quota available. With a non-NULL limit, `usage_count < usage_limit` must be true at the database write, not just at an earlier read.
- Increment `usage_count` exactly once in the same transaction as Order, OrderItems, voucher snapshot, Payment, Cart mutation, inventory and required audit. If any part fails, the increment rolls back. The final quota slot can be consumed by only one concurrent Order.
- A committed Order links to at most one Voucher via `ORDERS.voucher_id` and one `ORDER_VOUCHER_SNAPSHOTS` row. Same logical Order placement cannot consume again on retry: P1.6 owns order idempotency/replay, and quota consumption executes only on the first successful commit.
- NULL `usage_limit` means no global cap, but `usage_count` still records net committed uses. There is no per-customer cap or voucher usage ledger table.

### 7.2 Release on cancellation

- P1.5 defines the release operation; P1.7 decides whether/when an Order cancellation transition invokes it.
- When P1.7 determines a cancellation is eligible to restore quota, atomically decrement `usage_count` by exactly one for that Order's consumed Voucher. Guard `usage_count > 0`, tie release to the single eligible Order transition and include it in that transition's transaction/audit.
- Repeated cancellation/retry cannot decrement twice. The guard comes from P1.7's state transition and the transaction's single-consumption/release behavior; do not add a voucher usage ledger or per-account counter.
- Do not release quota by default for refund/return, quote, failed/uncommitted Order placement or an Order that did not consume a voucher. Do not require the Voucher to remain ACTIVE/in-window for a valid release of an already consumed use.
- If release transaction fails, Order transition and quota decrement both roll back. Do not decrement on a best-effort/asynchronous path after the Order transition has already committed.

## 8. Stable errors and acceptance

Use the existing API error envelope and deterministic domain codes, including `VOUCHER_NOT_FOUND`, `VOUCHER_NOT_ELIGIBLE`, `VOUCHER_WINDOW_INVALID`, `VOUCHER_MINIMUM_ORDER_NOT_MET`, `VOUCHER_USAGE_LIMIT_REACHED`, `VOUCHER_CONFIGURATION_INVALID`, `VOUCHER_QUOTA_CONFLICT`, `MONEY_OVERFLOW` and `MONEY_TOTAL_MISMATCH`. Do not expose SQL exceptions or accept client-computed monetary values as authoritative.

The focused acceptance cases are listed in [P1-test-matrix.md](P1-test-matrix.md). Required coverage includes HALF_UP boundaries, caps, deterministic line allocation, totals/Payment/report consistency, time boundaries, usage-limit races, duplicate Order retry, transaction rollback and one-time cancellation release.

## 9. Acceptance boundary

P1.5 freezes the documentation contract; it does not implement Strategy/engine, Voucher service, checkout UI, seed SQL, DDL or Order state transitions. The exact target-schema definition and runtime integration remain separate gates. P3.6/P3.7/P3.9 must implement formulas and quota transaction as written; P1.7 decides cancellation timing, and P1.6 decides order-create idempotency transport/replay.
