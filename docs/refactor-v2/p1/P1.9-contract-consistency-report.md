The `GOODS_RECEIPTS.warehouse_id` Data Dictionary row incorrectly cited `DB-04` and `OWNER_DIRECTION_RECORDED`. DB-04 refers to guest-checkout scope, not the warehouse FK. The row now cites `DB-03/A-04/P1-PROP-04` and records `OWNER_APPROVED_IMPLEMENTATION_PENDING`, aligned with the owner-approved one-operational-warehouse scope and P1.4’s server-resolved ACTIVE warehouse rule. Runtime mapping remains pending.

### 2.3 API, DTO and report/content semantics

The target API mapping now follows P1.8 where the prior mapping still reflected legacy runtime DTOs:

- Audit read uses target fields `id, actor_account_id, action, entity_type, entity_id, before_data, after_data, correlation_id, created_at`. Legacy `target_type/target_id/description` are not target fields; no new projection or schema field was invented.
- Public content reads are keyed by `slug`, expose only published content, and do not treat the legacy `pageCode` label as target identity.
- Report read-source descriptions are aligned with P1.8: completion period uses `SHIPPING_INFOS.delivered_at`; report formulas, current-state Order status and whole-Order return semantics remain owned by P1.5/P1.7/P1.8.
- Supplier route mapping no longer elevates a legacy controller/DTO cross-check to target authority. Runtime request/response acceptance remains pending.

### 2.4 Deletion and FK behavior against current target DDL

P1.8 and its runbook now state the non-destructive behavior compatible with the existing target DDL:

- There is no `ON DELETE CASCADE` in the target DDL. Permitted Cart working-data cleanup deletes `CART_ITEMS` before `CARTS` in one transaction. No cascade into business history is introduced.
- `ATTRIBUTES` and `ATTRIBUTE_OPTIONS` have no `status` or `deleted_at` field and P1.3 defines no DELETE route. Retain these rows and expose no delete route; any future schema-supported deletion capability requires an owner-approved ERD/schema amendment.
- Order, Payment, inventory ledger, audit and historical snapshot protections remain unchanged. Numeric retention/anonymization values remain TBD; no purge is authorized.
