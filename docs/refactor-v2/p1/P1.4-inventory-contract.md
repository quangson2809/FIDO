- P1.3 owns Product identity. All inventory/receipt lines and movements use `product_id`, never `variant_id`.

- P1.7 owns Order/Payment/Shipping state transitions and chooses when an approved Order command requests an inventory effect. P1.4 defines only the inventory service contract and does not decide Order transition timing.

## 2. Balance, bounds and version

### 2.1 Key and quantity

- A balance is identified by the composite key `(warehouse_id, product_id)`. It has no separate generated balance ID.
- `quantity_on_hand` represents physical on-hand stock, not a Cart/quote reservation and not a client-editable value. Its valid range is `0..2,147,483,647` (signed SQL INT).
- Each committed stock movement has a non-zero signed SQL INT `quantity_delta`. Reject underflow, signed-INT overflow and any update that cannot be represented in the target column.
- `version` is a server-owned, non-negative SQL INT concurrency counter. A never-mutated/missing balance is read as quantity 0/version 0. A persisted zero balance retains its actual version.
- A new balance row starts at version 0; every committed non-zero balance movement increments version exactly once. Reject version overflow. A version column without row locking or guarded comparison and an affected-row check does not prevent lost updates.

### 2.2 Missing balance

- **Read:** a missing `INVENTORIES` row means logical quantity 0/version 0 and never implies available stock. Reads do not create a row.
- **Positive movement:** in the transaction, insert a zero balance row if absent using insert-if-absent, then lock/re-read it and apply the movement. A concurrent insert must never overwrite quantity or reset version.
- **Negative movement:** missing/zero stock fails with a typed insufficient-stock conflict. Do not create a row to make a negative command succeed.
- **Failure:** source validation, guarded update, ledger insert, audit or commit failure rolls the entire transaction back, including any newly inserted zero row.
- No API or service may set a final balance directly. Initial stock is an `OPENING` movement; every later correction is another movement.

## 3. Approved movement types

The v1 set is closed. Reject unknown values and invalid type/sign/source combinations. The unique `idempotency_key` in the approved schema stores a server-derived semantic movement key, not merely a client transport retry key.

| Type | Sign and quantity | Required source / eligibility | Semantic duplicate and reversal rule |
|---|---|---|---|
| `OPENING` | Positive only | Explicit authorized opening command for one server-resolved warehouse/Product pair, with actor. | At most one opening movement per pair; derive key from type + warehouse ID + Product ID. Later corrections use ADJUSTMENT. |
| `GOODS_RECEIPT` | Positive; equals persisted `quantity_received` | One `GOODS_RECEIPT_ITEMS` row in the receipt being confirmed. Parent must win guarded DRAFT→CONFIRMED. | Derive key from receipt-item ID + type. Different request keys cannot post the same line twice. |
| `ORDER` | Negative; quantity derives from the OrderItem | Order owner requests the effect after its approved command revalidates current stock. P1.7 decides which transition triggers the effect. | Derive key from OrderItem ID + `ORDER`; guarded source state prevents a second deduction. |
| `ORDER_CANCEL_REVERSAL` | Positive; exact inverse of the original ORDER deduction | Links `order_item_id` and `reverses_transaction_id` to the same original ORDER deduction; requested only by authorized cancellation compensation. | Derive key from original movement ID + reversal type. At most one cancellation reversal per deduction. |
| `RETURN_RESTOCK` | Positive; no more than the eligible remaining quantity | Links the OrderItem and original ORDER deduction; requires a stable accepted-return-event identity from the Order-owning workflow and an authorized decision that the Product is sellable again. | Derive key from the accepted return-event identity, not just the HTTP retry key. Same event is posted at most once. P1.4 does not add a return table or define a return state machine. |
| `ADJUSTMENT` | Any non-zero signed delta | Authorized operator/system actor, Product, server-resolved warehouse and required `reason_code`; negative adjustment cannot overdraw stock. | Require stable `source_operation_id`; store a deterministic key such as `adjustment:<source_operation_id>`. Reuse the same operation ID across transport retries. Same ID/same canonical command replays; same ID/different payload conflicts. A genuinely new adjustment has a new operation ID. |

For a correction/reversal, the original ledger row remains immutable. When `reverses_transaction_id` represents an exact full correction, the new delta is the exact opposite of the original. Do not introduce a seventh movement type.

### 3.1 Source, actor and immutable event fields

- The service derives `transaction_type`, `quantity_delta`, source IDs, warehouse, Product, `created_by` and `created_at` from an authorized typed command and persisted source facts. Public callers cannot submit an arbitrary ledger row.
- Actor attribution comes from the authenticated principal or explicit system-event context; never trust a request's `created_by`.
- A GOODS_RECEIPT movement requires `goods_receipt_item_id`; ORDER, cancellation reversal and return restock require the applicable `order_item_id`. Validate the full parent relationship and source eligibility, not only FK existence.
- For a semantic key collision, compare the committed canonical type/source/warehouse/Product/delta/reason/reversal payload. Replay only if semantically identical; otherwise return a stable source/idempotency conflict.
- The physical schema does not define a reason-code enum. P1.4 freezes the required use of `reason_code`, not a new vocabulary; implementation must define and validate an owned controlled vocabulary before accepting arbitrary text.

## 4. Transaction, lock and failure contract

Every write that changes stock updates the source state when applicable, the balance/version, exactly one matching ledger movement and required audit in the same database transaction.

1. Authenticate/authorize, resolve the operational warehouse on the server and validate the typed source command. Callers cannot choose an arbitrary warehouse.
2. Lock the source aggregate first (receipt for a receipt command; the Order owner supplies an eligible Order command). Lock source lines in a stable order. Never acquire balance locks and then reach back to lock the source aggregate.
3. Lock every affected balance key in ascending `product_id` order (warehouse ID is a stable tie-break if a future approved scope expands). For a missing positive-stock key, insert-if-absent, then lock/re-read it.
4. Validate source status, source/product/warehouse match and optional `expected_version` under the lock. A stale expected version returns a stable conflict; the server-side lock/current version is still required when the precondition is omitted.
5. Apply a guarded update equivalent to `0 <= quantity_on_hand + delta <= 2147483647` and `version = current_version`, incrementing version once. Exactly one row must be updated.
6. Insert one ledger row with the server-derived semantic key and validate type/sign/source/reversal invariants. A unique-key collision aborts this transaction; after rollback, read the winner and replay only if the canonical command matches.
7. Write required audit using server actor/correlation context. Commit source state, balance, ledger and audit together.

Consistent lock order across Inventory callers is source aggregate → source lines in stable order → balance keys by ascending Product ID → ledger/audit append. The Order owner may already hold its source lock before calling Inventory. Inventory must never bypass another module's Repository or acquire locks in reverse order. Deadlock, lock timeout, stale version, source collision, insufficient stock, overflow or audit failure must not leave partial state.

## 5. Receipt lifecycle and use cases

- Supplier lifecycle is `ACTIVE`/`INACTIVE`; only an ACTIVE Supplier can be selected for a new receipt draft. Disabling does not erase historical receipts.
- In v1, the server resolves exactly one operational ACTIVE warehouse. Receipt creation stores that destination; confirmation must not silently redirect stock. If operational warehouse resolution is missing or ambiguous, fail closed with a configuration error.
- GoodsReceipt is `DRAFT`, `CONFIRMED` or `CANCELLED`. Only DRAFT is editable. Confirm requires at least one valid Product line; each line has positive quantity and non-negative integer-VND `unit_cost`; one Product line per receipt.
- Create/edit draft has no stock or ledger effects. Confirmation atomically claims DRAFT→CONFIRMED, posts one positive GOODS_RECEIPT movement per line, updates balances/version, sets confirmed actor/time and writes audit. Concurrent/repeated confirms post once; a successful retry returns/replays the committed result. CANCEL is DRAFT-only and has no stock effect.
- CONFIRMED and CANCELLED receipts are terminal; their facts/lines cannot be edited. A correction to a confirmed receipt is a new authorized movement, never a second confirmation.

| Target UC | Precondition and action | Postcondition / rejection |
|---|---|---|
| `INV-UC-01` Read inventory | Actor has inventory-read permission. | Product-level on-hand/version and paginated ledger; absent balance displays 0/0. Read does not reserve stock or write ledger. |
| `INV-UC-02` Maintain supplier | Actor has inventory-write permission. | Create/update supplier; inactive supplier cannot be selected for a new receipt. Historical references remain. |
| `INV-UC-03` Create/edit receipt draft | Authorized actor; valid supplier/Product references. | DRAFT only; `product_id`, positive `quantity_received`, non-negative integer-VND `unit_cost`; server sets receipt number/actor/warehouse. No stock side effect. |
| `INV-UC-04` Confirm receipt | Receipt DRAFT with at least one valid line. | One DRAFT→CONFIRMED transition and one movement per receipt item with balance/ledger/audit atomic. Repeated/concurrent confirm cannot post twice. |
| `INV-UC-05` Cancel draft receipt | Receipt is DRAFT. | DRAFT→CANCELLED, no inventory movement. Terminal receipt cannot be edited/cancelled again. |
| `INV-UC-06` Adjust inventory | Authorized actor; Product, non-zero delta, reason and stable source operation ID. | Apply signed movement and audit atomically; reject stale version, underflow/overflow, changed payload for same operation ID and unauthorized action. |
| `INV-UC-07` Open stock | Explicit authorized initialization. | One positive OPENING movement per warehouse/Product pair; never set quantity directly. |
| `INV-UC-08` Apply reversal/return restock | Authorized source-owning workflow and valid original movement. | Append positive linked movement that satisfies source/sign/cap rules. Reject missing/mismatched original, over-restock or duplicate source event. |
| `INV-UC-09` Reconcile | Inventory operator/system report. | Verify balance equals ledger sum and version equals committed movement count from zero baseline; report mismatch without rewriting history. |

P1.4 does not decide which Order transition invokes Inventory. P1.7 owns that decision; its Order orchestration calls the Inventory service after its own approved preconditions and includes the effect in the enclosing transaction. P1.5 owns money/voucher rules.

## 6. Reconciliation and API handoff

- From a zero target baseline where all opening stock is recorded as OPENING, `quantity_on_hand = SUM(INVENTORY_TRANSACTIONS.quantity_delta)` per warehouse/Product. A missing balance and no movements both reconcile to zero.
- From the same baseline, version equals the count of committed balance-changing movements for the key. A reconciliation process reports discrepancies; it never silently updates a balance or edits ledger history.
- The canonical API paths/permission gates remain in [04-api-contract.md](../../04-api-contract.md) and API-46–57 in [P1-api-contract-mapping.csv](P1-api-contract-mapping.csv). Adjustment accepts `product_id`, non-zero signed `quantity_delta`, `reason_code`, stable `source_operation_id` and optional `expected_version`; no client-selected warehouse, actor, final balance or source movement type.
- Stable domain error examples: `INVENTORY_INSUFFICIENT_STOCK`, `INVENTORY_STALE_VERSION`, `INVENTORY_BALANCE_OVERFLOW`, `INVENTORY_SOURCE_CONFLICT`, `INVENTORY_IDEMPOTENCY_CONFLICT`, `INVENTORY_INVALID_MOVEMENT`, `INVENTORY_WAREHOUSE_CONFIGURATION`, `GOODS_RECEIPT_INVALID_STATE`, `GOODS_RECEIPT_EMPTY`. Use the existing API error envelope; do not expose SQL details.
